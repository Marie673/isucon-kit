# 過去問の頻出パターン

詳しくは `docs/tuning/README.md`。

すべて「仕様が許すなら」。docs/RULES.md に出典がない余地は使わない。

## ポーリング / 通知（過去の回で勝敗を分けた）

- クライアントが一定間隔で叩く API は、レスポンスで次の間隔を指示できることがある（`retry_after_ms`、`Retry-After` 等）
  - 間隔を延ばす → リクエストが減り CPU が空く。ただし延ばしすぎると加点イベントの反映が遅れて点が落ちる
  - 過去の優勝解には、通知の間隔調整で伸びたものがある
- 通知の配信を非同期キュー + 固定ワーカーにし、**ペーシング**（少数には早く、残りは遅く）する
- SSE / ロングポーリングに変えられるか、仕様を確認する
- 「ちょうどいい圧」がある。絞りすぎると下がった実例あり → 数段階を単独でベンチして山を探す

## マッチング / 割り当て

- 定期実行のマッチング（cron 的な API 呼び出し）は、間隔とアルゴリズム（最近傍・貪欲）がスコアに直結する
- 全件を毎回走査しない。空き状態をメモリで持つ

## 一覧・ランキング・検索

- 書き込み時にソート済み構造（スライス / BTree）を更新し、読み出しは切り出すだけ
- ページングの `OFFSET` が大きいならカーソル方式（仕様が許すなら）

## 画像・ファイル

- DB の BLOB → ファイルに書き出し nginx で配信。ハッシュ（ETag）が必要なら書き込み時に計算して保存

## 認証・セッション

- セッション → ユーザーの対応をメモリで持つ
- bcrypt のコストは仕様で固定のことが多い。結果をキャッシュできるか（同じ入力が繰り返されるか）を確認

## 待ちで伸びないとき（idle が多い）

- アプリ内の `sleep`、ベンチ側のポーリング間隔、外部サービスの待ち、ワーカー数の上限、DB のロック待ちを疑う
- ログを足して「どのリクエストが何ms待っているか」を数字にする（実例: 「無駄な通知」仮説がログで「409 の嵐」に置き換わった）

## initialize

- 制限時間内に終わること。重い初期化（キャッシュ構築・画像の書き出し）はここに置く
- インメモリ実装は initialize で seed から状態を作り直し、delta を捨てる
