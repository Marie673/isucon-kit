# isu-analyze — 計測結果から仮説へ

## 読む順番

1. `results/<id>/SUMMARY.md` の **CPU 表とプロセス別 CPU** — 何が CPU を食っているか
   - mysqld が支配的 → DB 起点（スロークエリ表へ）
   - アプリが支配的 → アプリ起点（perf と alp へ）
   - idle が多いのにスコアが低い → 待ち（ロック・外部呼び出し・sleep・ポーリング間隔・ワーカー数）を疑う
   - wa が高い → ディスク I/O（innodb の flush、ログ出力）
2. **alp（合計時間順）** — 上位エンドポイントが「回数 × 平均」のどちらで重いか
   - 回数が多い → キャッシュ、まとめ取り、レスポンスの軽量化、ポーリング間隔（仕様の余地を RULES.md で確認）
   - 平均が遅い → そのハンドラのクエリと計算量
   - 4xx / 5xx の急増は性能より先に直す（失格・減点の芽）。409 や 429 の嵐は「仕様上の競合」かもしれない（ログを足して数字にする）
3. **スロークエリ（Profile）** — Rank 上位の `Calls` と `R/Call`
   - Calls が桁違いに多い → N+1（ハンドラのループ内クエリ）
   - R/Call が大きい → インデックス不足、全件走査、ソート、`LIKE '%..'`
   - 詳細は `<db>/slow.txt` の該当クエリの `EXPLAIN` 相当を読む。必要なら `bin/isu-ssh <db> "sudo mysql <db> -e 'EXPLAIN ...'"`
4. **perf** — comm 列でプロセス、symbol で関数。JSON エンコード、正規表現、bcrypt、GC、テンプレートが上位に来る常連
5. **アプリログ** — エラーの件数と種類

## 仮説の書き方（1仮説 = 1タスク）

```sh
bin/isu-task add "<何を>: <どこを>" -p <0-3> -d "根拠: results/<id> の <表> で <数値>。
見込み: <どれくらい減るか>。リスク: <壊しうる仕様>。触るパス: <files>。検証: <どう確かめるか>"
```

- 優先度は「見込み ÷ 手間」と「リスクの低さ」で決める。インデックス・N+1 は p0〜1 の常連
- 根拠の数字がない仮説は「仮説: ログを足して数字にする」タスクにする（例: どのユーザーが何回 409 を受けているか）

## 2つの結果を比べる

- スコア差、上位エンドポイントの順位と sum の変化、スロークエリ上位の入れ替わり、CPU 配分の変化を並べる
- スコアが上がらないのにボトルネックが消えた → 次のボトルネックが別の場所に移った。CPU 表で探す
- スコアが下がった → エラー件数とベンチ出力を先に見る（整合性で落ちていないか）

## やらないこと

- 計測していない場所の推測による最適化
- 1回のベンチでの細かい差（±数%）を結論にすること。ばらつきの範囲か、もう1回で確かめる
