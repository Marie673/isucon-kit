# 傾向を掴む実験

## なぜ要るか

止まっている理由（その資源か、ベンチ側の上限か）は、改善を積んでからでは、ぶれに埋もれて分からない。**ボトルネックを一時的に外して、外した後の伸び方を見る**実験を序盤に数本入れると、何を直すべきかが早く決まる。

## 前提（当日のマニュアルで必ず確かめる）

- 最終のスコアは、最後に流したベンチのスコア。途中のベンチのスコア・FAIL は最終のスコアに入らない。→ 序盤〜15:00 のベンチは実験に使ってよい。
- **競技サーバーのスペックアップ・サーバーの追加はできない**。スコアを上げる外部資源・複数の環境の利用も不可。
- 開発・テストに外部のサーバーを使うのは可。→ 資源を「足す」実験は手元（`tools/lab-aws`）でだけやる。
- **ベンチのリクエストを、一時的にでも大きな外部のサーバーへ流さない。** 外部資源の使用・処理の委譲の禁止に、時点の限定があるかをマニュアルで読む。限定が無ければ、途中のベンチでも例外にしない。
  - どうしても要るなら、当日にポータルの質問で主催者に確かめる。答えが出るまでやらない。失格はチーム全体に効く。
- 同じ問い（資源が十分ならどこまで伸びるか）には、次の 2 つで答える。
  - **競技サーバーの中で寄せる**: 複数台の CPU を、調べたい区分・処理に片寄せる（相手のサーバーにはプライベート IP で接続する）。その区分から見れば「大きなサーバー」になる。他の区分のスコアは下がってよい。
  - **手元で上げる**: capture したベンチのリクエストを、本番と同じ系統の大きなサーバー（`tools/lab-aws`）で再生する。ただし再生は開ループ（応答を見て次の行動を変えない）で、利用者の増え方は再現しない。増え方まで見たいときは、`docs/design.md` の B の動線どおりに動く閉ループの負荷生成を作る。

## ベンチの FAIL とチームの失格を分ける

ボトルネックを一時的に外す実験の可否は、この区別で決まる。

| 段 | 扱い | 例 |
|---|---|---|
| A. 安全に外す | スコアが下がるだけ | 資源をサーバーの中で片側に寄せる、OTel・ログを切る、接続数・並列の上限を上げる、遅延を足す |
| B. ベンチが FAIL しうる外し方 | **途中のベンチならよい**。そのベンチが 0 点になるだけ（最終のスコアは最後のベンチで決まる） | 重い検査を軽くする、計算の結果を覚えて使い回す、重い低配点の処理をピークの間だけ止める |
| C. やらない | チームの失格・主催者への迷惑 | 外部のサーバーに流す、スペックアップ、ルーターの迂回、固定の応答で整合性の検証を避ける・ベンチだけを見分けて違う結果を返す、**わざと誤った応答を返してベンチの検査を探る**、**主催者のサービス（決済・外部 API など）に負荷をかける実験** |

B を選ぶときの条件。

- **全利用者に同じ動きをする、本物の実装のまま軽くする。** 固定の応答・ベンチの見分けは C。
- **クリティカルエラーを起こさない外し方を選ぶ**。起こすとベンチがその場で打ち切られ、観測したい最後の日まで届かない。整合性に関係しない重い仕事（検査・署名・計測）を軽くするのは、たいてい検証の失敗が起きないか、エラーとして数えられるだけで済む。
- 実験の変更は main に入れない（下の手順 4）。最後のベンチには絶対に乗せない。

## 実験の種類

| 種類 | やること | 答える問い | 場所 | 壊す危険 |
|---|---|---|---|---|
| **引く** | 必須だが重い仕事を一時的に軽くする・外す（例: 検査を構造だけに、署名を覚えて使い回す、ログ・トレースを切る） | この仕事を無くしたら、人数・スコアはどこまで伸びるか（＝このボトルネックの天井）。ボトルネックが無いときの 1 人あたりの操作の数（capture で） | 競技サーバー | 上の B。クリティカルエラーに触れない仕事だけを選ぶ |
| **足す（遅延）** | ある API に、わざと sleep を足す（50ms・200ms・1s） | この API の速さは、人数の増え方に効いているか（感度）。効かないなら直してもスコアは伸びない | 競技サーバー | 小さい。スコアが下がるだけ |
| **寄せる** | 複数サーバーの資源を、ある区分・ある処理に片寄せる（例: 1区分の処理を全部空いたサーバーへ） | その区分のボトルネックを外すと、その区分の人数は増えるか。増えなければ、ボトルネックではなく上限 | 競技サーバー | 他の区分のスコアが下がる |
| **上げる（スペック）** | 本番と同じ系統の CPU の大きなサーバーで、capture の再生か手元の負荷生成を流す | 資源が十分なとき、アプリのどこが次のボトルネックか。CPU を何倍にすればピークを捌けるか | 手元（`tools/lab-aws`） | 無し（費用だけ。人間が事前に決めた範囲でだけ。無ければ使わない） |
| **測る（上限）** | 区分 × 日の人数をベンチごとに並べ、規模の違うベンチで同じ所で止まるかを見る | 人数に上限があるか | 記録だけ | 無し |

## 手順

1. **問いを 1 つ書く。** `docs/design.md` の B5 か、ボトルネック表の「保留」から。問いの無い実験はしない。
2. **予想を先に書く。** 「このボトルネックを外せば、最大の区分の最後の段階の件数が 2 倍になる」など。予想と結果の差が学び。
3. **実験を選ぶ。** 上の表から、問いに直接答え、整合性に触れないものを選ぶ。
4. **ブランチと台帳。** 実験の変更は `probe/<名前>` のブランチ（worktree）で作り（subagent に渡してよい。skill `delegate`）、`docs/flags.md` に状態 `probe` で載せる。**main にはマージしない。** メインエージェントがその worktree から `bin/isu-bench start --probe --note "probe: <問い>"` を流す（`isu-bench` は起動した checkout の HEAD を反映し、結果は main の `results/` に branch つきで残る）。終わったら、main の checkout から次のベンチを流して元に戻す。
5. **流して読む。** 点だけでなく、区分 × 日の人数、段階ごとの成功、ピークの窓（`tools/bench-window/bench-window`）を見る。ぶれの幅（`tools/noise`）と比べる。
6. **記録する。** `docs/experiments.md` の「実験」に、問い・予想・結果・結論を 1 行で。ボトルネック表の順番を直す（メインエージェント）。

## いつやるか

- **10:30〜12:00（ベースラインの後、構成の判断の前）に 2〜4 本。** 構成の判断の材料になる。
- ボトルネックが移ったと思ったときに 1 本（15:00 の見直しの前）。
- **15:00 以降はやらない。** 凍結に向けて、最後のベンチを壊さないことを優先する。

## 序盤にやると答えが出る実験（型）

| 問い | 実験 | 分かること |
|---|---|---|
| この頭打ちはボトルネックか、ベンチ側の上限か | 引く＋寄せる: 疑う資源の重い処理を一時的に軽くし、計測も切る。そのベンチを capture する | 超えればボトルネック、超えなければ上限。ボトルネックが無いときの動線と操作の数 |
| この API の速さはスコアの項に効くか | 足す: その API に遅延を足す | 効かないなら直してもスコアは伸びない |
| ピークを捌くのに CPU は何倍要るか | 上げる: 手元の大きなサーバーでピークを再生 | 構成を変えるべきか、積み増しで足りるか |

## 守ること

- 整合性の検査・失格の条件（`docs/RULES.md`）に触れる実験はしない。ベンチを見分けて違う応答を返すことは、実験でもしない。
- **わざと誤った応答を返して、ベンチが何を検査しているかを探らない。** ベンチの検査は、マニュアルと仕様書（`docs/design.md` の A）から読む。
- **主催者のサービス（決済・外部 API・ポータル）に負荷をかけない。** そこへの同時数・再送を増やす変更は、実験でも入れない。主催者のサービスが詰まると、他のチーム・ベンチ全体に響く。主催者のサービスへの同時数は、マニュアルの記述の範囲で決め、決めた理由を `docs/DECISIONS.md` に書く。
- ベンチの処理を、競技サーバー以外へ出さない（途中のベンチでも禁止事項に当たると読む。上の「前提」）。
- 実験の変更を main に残さない。終わったら元に戻した状態のベンチを 1 回流して、戻ったことを確かめる。
- 手元でサーバーを借りるのは、人間が承認した範囲（台数・種類・時間・費用）だけ。

probe の worktree からは start・finish・abort・wait のすべてに `--probe` を付ける。
