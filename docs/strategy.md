# 作戦（REV 4）

見る → 説明する → 理屈で形を決める → 施策を打つ。
判断の数字と仕事の順番は docs/README.md の作戦ボードへ集める。
仕様は docs/RULES.md、設計は docs/design.md、判断は docs/DECISIONS.md、比較は docs/experiments.md に残す。

## 方向の決まり

1. 最初に利用者の動きとスコアのモデルを書く。マニュアルとログを照らす。
2. 説明できない所は、問題に依らない引く・遅延を足す・資源を寄せる実験で確かめる。
3. ボトルネック表の先頭を今のボトルネックにする。根拠の数字を添える。
4. スコアの式の項ごとに取りこぼしを数える。区分・段階・理由を分ける。
5. ピークの処理量と1要求の仕事量から資源を計算する。初期構成と制約に合う構成を比べる。
6. 目標の点で止めず、凍結まで効く項を止めるものを取り除く。

## 流れの決まり

1. 同じ条件を複数回測る。平均の差は tools/noise/noise -f results/SCOREBOARD.md compare A B で読む。交互なら --paired を使う。
2. 比べたい変更は一度に1つにする。信頼区間が0を含む場合は、プロファイルと項ごとの数字も使う。
3. フラグは tools/flags/flags --ledger docs/flags.md で記録する。
4. bin/isu-bench start → skill portal-bench → bin/isu-bench finish の順で確定する。終了の正はポータルの job にする。
5. 判断の数字をベンチごとに作戦ボードへ集める。却下した案の前提が崩れたら判断を出し直す。
6. 守る条件は道具に持たせる。排他はロック、宣言したパスは bin/isu-intake、永続化の記録は flags durability が確かめる。

## 実装と判断

main の canonical checkout に反映と結果を集める。
小さな変更は直接入れる。
独立した実装・調べもの・検証は subagent に渡せる。
返ってきたブランチは宣言したパスを bin/isu-intake で確かめてから読む。
判断は「見たもの → 考え → 決めたこと」の3段で書く。
撤回の条件と確かめ方を添える。
人間に聞かずに決める。費用だけは事前に決めた範囲を守る。

## 終盤とコンテキスト

時刻は isu.env の ISU_END_AT・ISU_FREEZE_AT と docs/RULES.md の終盤の時刻表を正にする。
再起動試験でサービスとデータが戻ることを確かめる。
凍結後の最終ベンチは --no-deploy --no-measure で同じ版を測る。
止め時は tools/stop-rule/stop-rule で考える。
終了の60秒前から道具は接続を拒否する。長い処理はそれ以前に終える。
自動 compact を前提に決めたことを docs/ に書く。
compact の後は作戦ボードから読み直す。
人間が操作できるときの /compact は任意。モデルから組み込みコマンドは呼べない。
