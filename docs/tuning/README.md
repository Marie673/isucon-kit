# ISUCON チューニングマニュアル

層ごとに「何を確かめ、どの設定・実装をどう変え、何が危ないか」をまとめた手引き。16 章・約 400 項目・出典の URL 約 450 件（2026-11-01 作成）。ISUCON の公式の講評・解説、出題者や常連の記事、上位チームの参加記、各ソフトウェアの公式ドキュメント、私たちの過去の実例から作った。

**当日のマニュアル・レギュレーションが常に優先する。** ここに書いた手が、その回のルールで禁止・失格になることがある（永続化を捨てる、外部へ処理を委譲する、静的ファイルを変える、ベンチを見分ける、など）。

## 使い方

- **最初に読むのはこのマニュアルではない。** 当日の最初の 90 分は、アプリの特性・スコアのモデル・山のキャパシティ・ボトルネック表を作る（[../strategy.md](../strategy.md)）。このマニュアルは、ボトルネックが分かった後に「その層で何をするか」を引くためのもの。
- 各項目は「効く条件 / やり方 / 確かめ方 / 危険 / 出典」の形。**効く条件が手元の計測で満たされているか**を先に確かめる。
- 入口は [isu-playbook](../../template/.agents/skills/isu-playbook/SKILL.md) にある。
- 出典に「出典未確認」とある箇所（全 16 章で約 140 か所。各章の末尾に一覧）は、資料で確かめられなかったもの。使う前に確かめる。参加記の数字は要約ツール経由で読んだものがあり、使う前に原文を確かめる。

## 当日の最初の 30 分に「読む」もの（変える前に）

各章の「最初に見るもの」から抜き出した。どれも読み取りだけで、変更はしない。

1. **再起動試験と永続化の決まり**をマニュアルで確かめる（何を再起動し、いつデータを確かめるか）。永続化に関わる設定に触る前に必ず — 15、04 / 05
2. 計測の仕込み（アクセスログに応答時間の列、スロークエリ、プロファイラ）。ベースラインの 1 本で全部そろうよう、ベンチの前に終える — 01
3. 各台の版と設定を読む: `nginx -V`・`nginx -T`、DB の版とバッファ・接続数・永続化の設定（`SHOW VARIABLES`・`SHOW ...`）、`/proc/cpuinfo`（`tools/cpu-features`）、`free`・`df`、`systemctl list-units` — 02、03、04 / 05、11
4. 接続数の掛け算: アプリの台数 × プロセス数 × プールの上限 と、DB の `max_connections` — 04 / 05、09
5. ベースラインの後: スロークエリの合計時間の上位、アクセスログの合計時間の上位、499・502・504 の数 — 01、06、03

## ボトルネックを調べる前でも入れてよい「床上げ」の手

計測を邪魔せず、戻しやすく、効く場面が多いもの。それでも、入れたらベンチ 1 本で壊れていないことを確かめる。

1. ファイルディスクリプタ・接続の上限（`LimitNOFILE`、`worker_connections`・`worker_rlimit_nofile`、`somaxconn`）— 02、03
2. nginx の upstream の keepalive（`proxy_http_version 1.1`・`Connection ""`）と、静的ファイルを nginx から直接返す — 03、12
3. DB のバッファの大きさ（メモリの配分の中で）と、アプリのプールの上限 — 04 / 05、09
4. 明らかな N+1 と、インデックスの無い検索（スロークエリの上位から） — 06
5. 計測・トレースの採取率を絞る（100% のトレースは CPU を約 1 割使った）— 01

**床上げに入れないもの**: 永続化を弱める設定（`innodb_flush_log_at_trx_commit`・`sync_binlog`・`synchronous_commit`・`fsync`・UNLOGGED・`vm.dirty_*` を大きく）。点は上がりやすいが、再起動試験・追試でデータが消えると失格になる。入れるなら、マニュアルの再起動試験の方法を確かめ、メインエージェントが理由・危険・撤回の条件を記録して判断する（04、05、02、15）。
