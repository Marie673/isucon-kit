# 16 置き換えと書き換えの判断

## この章で扱う範囲

- 初期実装の言語から Go・Rust へ置き換える価値と、かかる時間。
- 互換テスト（応答の突き合わせ）と、パス単位の段階的な切り替え。
- 全面インメモリ化への書き換えの判断と、着手の時刻。
- 過去の上位チームがいつ・何を書き換えたかと、失敗例。

扱わないもの: プロセス内キャッシュの設計と無効化（08 章）、Go と Rust のランタイム設定（09 章）、再起動試験の手順（15 章）。

## 最初に見るもの（当日の判断のチェックリスト）

置き換えと書き換えは、**計測で「アプリの CPU がボトルネック」と分かってから**決める。DB のインデックス・N+1・配置を直す前に言語を替えても、点はほとんど動かない（下の「置き換えの価値」）。

| 見るもの | 何を確かめるか | 判断への使い方 |
| --- | --- | --- |
| プロファイル上のアプリの CPU の割合 | アプリ CPU（JSON・ハッシュ・画像・テンプレート）と DB・待ちのどちらが大きいか | アプリが小さければ、置き換えない |
| チームがその言語で書けるか | 慣れていない言語で、型・ライブラリ・非同期の扱いに時間が溶けないか | ISUCON12 の dyoshikawa は、Ruby から Go へ替えて Go に慣れず、最終 3,160 点 |
| 残り時間と凍結の時刻 | 凍結（最終ベンチ）までに、置き換え・テスト・再起動試験が入るか | 入らないなら始めない。小さく出せるものを先に出す |
| 規則 | 再実装・サービスの追加が許されるか。再起動後の永続化。外部委譲の禁止 | 許されないなら、そもそも選べない |

## 言語の置き換え

### 置き換えの価値を見積もる

- **効く条件**: プロファイルで、アプリの CPU（JSON・ハッシュ・テンプレート・正規表現・GC）が上位で、DB のインデックス・N+1 は直した後。初期実装が prefork の遅い言語（Ruby・Python・Perl・PHP）で、ワーカー数の調整でも足りない。
- **やり方**: 次の根拠を並べて、置き換えの見込みを決める。

| 根拠 | 内容 |
| --- | --- |
| 公式の講評（ISUCON14） | インデックスを足すだけで、Go の実装では約 4,000 点まで伸びる。JSON API のままでも、ライドのキャッシュなどで、試し解きで少なくとも 10 万点を取れた。言語の比較は無い |
| 公式の講評（ISUCON13） | 初期スコアは言語によって約 3,000 点でばらつき、インデックスの追加で約 10,000 点まで上がった |
| 公式の講評（ISUCON12 予選） | prefork 型の言語は初期スコアが低い。ワーカー数を 30〜50 に増やすと改善する |
| 本選の言語別の結果（ISUCON14） | 787 チームのうち Go 549・Node.js 69・Ruby 64・Python 48・Rust 27・PHP 24・Perl 4（全部 FAIL）。最高は Go 58,153、Rust 36,810、Ruby 36,300、PHP 31,002、Node.js 25,411、Python 13,033 |
| 上位帯の言語（ISUCON13） | 上位 30 チームのうち Go が 29（96.7%）、Ruby が 1。Rust は 25 チーム（3.8%） |
| ISUCON12 本選 Dice801（Rust） | 10:18 に Rust に替えて 575→703 点（約 +22%）。大きく動いたのは、インデックスと N+1 の修正（11:38 に 7,035 点）、アプリと DB の分離（12:25 に 20,272 点）、ユーザー ID での DB の分割（17:33 に 101,647 点） |

- **確かめ方**: 同じ commit・同じ設定で、言語だけを変えて 3 本流す。差が走行のぶれ（±10〜15%、低い点では ±30%）を超えるか。
- **危険**
  - 言語別の順位は、言語の速さではなく、参加者の数と慣れの差を含む。ISUCON14 は総合の上位 5 位が Go（5 位の 43,888 点が、他の言語の最高 36,810 点より上）だが、Go のチームが多いだけとも読める（因果は出典に無い。出典未確認）。
  - 置き換えだけで速くなるとは限らない。外部画像変換をライブラリ化しても得点がほぼ横ばいだった例がある（ISUCON3 本選）。
  - 置き換えている間は、その人の時間を言語に依存しない改善（インデックス・N+1・設定）に使えない。
- **出典**: [ISUCON14 の講評](https://isucon.net/archives/58869617.html)、[ISUCON14 の利用言語比率](https://isucon.net/archives/58847106.html)、[ISUCON13 の講評](https://isucon.net/archives/58001272.html)、[ISUCON13 の利用言語比率](https://isucon.net/archives/57995340.html)、[ISUCON12 予選の講評](https://isucon.net/archives/56850281.html)、[Dice801 の ISUCON12 本選](https://zenn.dev/dice801/articles/ebc027207257b1)、[dyoshikawa の ISUCON13](https://zenn.dev/dyoshikawa/articles/isucon-13-dyoshikawa)。

### 置き換えにかかる時間（実例）

- **効く条件**: 置き換えると決めた。時間の見積もりが要る。
- **やり方**: 次の実例から、チームの条件に近いものを選ぶ。

| 実例 | かかった時間・結果 |
| --- | --- |
| INUCON | 12:00〜13:30 に、移植用の Agent Skill とエンドポイントごとの subagent の並列で移植。最初の Go 版は Rust と同程度でベンチを通った。計測の開始は 1.5 時間後 |
| kawaemon（ISUCON14 の感想戦。Go ではなく Rust の初期実装を作り直した） | 約 1 か月。まずリファクタ（型・DB 呼び出しのリポジトリ化）をして、その後に DB を外した。**リファクタ前に最適化しようとして失敗し、コードを作り直した**（12/9〜11） |
| dyoshikawa（ISUCON12。Ruby から Go） | 途中で Go に替えたが、Go に不慣れで、最終 3,160 点（ISUCON13 は最初から Go で 3,500→10,500 点） |

- **確かめ方**: 置き換えの「着手時刻」「ベンチが通った時刻」「その後の点」を記録し、見積もりと比べる。
- **危険**: 移植用と元の実装が併存すると、エージェントが別のコードを直す（INUCON は「一番良くなかった」と書く）。作業先とデプロイ元を 1 つに決める。

### 置き換えない判断

- **効く条件**: DB のインデックス・N+1・配置・キャッシュで、まだ点が動く。プロファイルでアプリの CPU が小さい。
- **やり方**: 次の順で、言語に依存しない改善を先にやる（置き換えの後にも効くので、無駄にならない）。
  1. インデックス・N+1・一括（06 章）。ISUCON13・ISUCON14 の公式の講評は、最初のボトルネックをインデックス・N+1とした。
  2. 配置・分離・キャッシュ（08・11 章）。
  3. アプリの CPU（09 章）。
  4. そのうえで、残る CPU が言語の差で下がるかを見る。
- **確かめ方**: ボトルネック表（`bottleneck-ledger`）の順位。アプリの CPU が上位でなければ、置き換えない。
- **出典**: [ISUCON14 の講評](https://isucon.net/archives/58869617.html)、[ISUCON13 の講評](https://isucon.net/archives/58001272.html)。

## 互換テスト（応答の突き合わせ）

### 置き換えの前に、初期実装の応答を記録して突き合わせる

- **効く条件**: 言語・フレームワークを置き換える、または大きく書き直す。ベンチは失格・減点の検知が粗く、原因の切り分けに向かない。
- **やり方**
  1. 初期実装を `/initialize` 直後の状態で起動して、ケースを流して応答を記録する（golden）。
  2. 置き換え後の実装に同じケースを流して、突き合わせる。
  ```sh
  C=.claude/skills/rust-replace/scripts/compat-check   # 手元のスキルの道具
  $C record --base http://127.0.0.1:<初期実装> --cases tests/compat/cases.jsonl --out tests/compat/golden.jsonl
  $C check  --base http://127.0.0.1:<置き換え後> --golden tests/compat/golden.jsonl
  ```
  3. ケースの出どころ: ベンチのリクエストの記録、API の一覧（1 本以上 + 境界）、ベンチが叩く異常系、アクセスログで多いもの、一連の流れ（登録→ログイン→操作→確認→取り消し）。
  4. **境界を入れる**: 在庫がちょうど埋まる・1 つ余る、同じ値の範囲指定や逆順、日時の端、件数の上限と下限、必須パラメータの欠落、二重操作。
  5. ケースの値は決め打ちにする（乱数・現在時刻を入れない）。実装で値が違う採番は `capture` で吸収し、毎回変わる項目は `ignore` に書く。
  6. **決定的か確かめる**: 初期実装に対して `/initialize` からやり直して 2 回流し、全部一致すること。
- **確かめ方**: 一致数、決定性（2 回の一致）。並走で `check` を回す。
- **危険**
  - 並列の二重予約などは、競争で応答が変わるので `compat-check` ではなく並行のテスト（race・repeat-run）で確かめる。
  - 壊れやすい点: パスワードの保存方法（変えない）、セッション Cookie の形式、JSON の数値・日時・`null`、ロックの範囲（`FOR UPDATE` の対象）、初期化 API の時間、応答の項目（`language` を空にしない）。
  - DB のエラー（デッドロック）で、画像のフォールバックなど「成功に見える応答」を返すと、仕様違反で失格になる（ISUCON13 の myuon: 約 80,000 点が約 10,000 点に落ちた）。

### 複雑な処理は、旧実装との突き合わせを別のデータで確かめる

- **効く条件**: 友達の友達のフィード・ランキング・配車のように、ロジックが複雑で、SQL や集計に書き換えた。
- **確かめ方**: 一致数。外れた入力を残す。
- **危険**: 一致を確かめたデータと、本番のデータの分布が違う。

## 段階的な切り替え

### パス単位で nginx で振り分ける

- **効く条件**: 初期実装と置き換え後を並べて動かし、パスごとに切り替える。2 つの実装が同じ DB・同じセッションの形式（Cookie）を使える。
- **やり方**: 2 つの upstream を作り、`map` でパスごとに向け先を決める。初期実装は止めずに残し、戻すのは 1 行を消すだけにする。
  ```nginx
  upstream app_orig { server 127.0.0.1:8080; keepalive 64; }
  upstream app_new  { server 127.0.0.1:8081; keepalive 64; }

  map $uri $backend {
      default                  app_orig;
      # ~^/api/stations$       app_new;   # 互換・critical が通った API から 1 つずつ
      # ~^/api/                app_new;   # 最後に API 全部
  }
  server {
      location / {
          proxy_http_version 1.1;
          proxy_set_header Connection "";
          proxy_set_header Host $host;
          proxy_pass http://$backend;
      }
  }
  ```
  段階は、次の順で通す条件を決める。

| 段階 | 何をする | 通す条件 |
| --- | --- | --- |
| A. 手元で並走 | 置き換え後を別ポートで起動し、互換テストの `check` | 全部一致 |
| B. テスト | critical・race・repeat-run を置き換え後へ向ける | 全部緑・間欠なし |
| C. 手元のベンチ | ベンチが配られていれば手元で流す | pass を 3 回連続 |
| D. 競技サーバーで一部 | 読み取り系の API から nginx で切り替える | 同じ構成（commit・設定・切替範囲）で本番ベンチの pass が 5 回中 5 回、初期化の秒数が上限の半分以内 |
| E. 全部切り替え | 書き込み系も向ける。最後に再起動試験 | 再起動後も正常でデータが残る。pass 率とスコアが初期実装を下回らない |

- **確かめ方**: どちらが返したかが、アクセスログから分かるようにする（ログのフィールドに `$backend` を入れる）。段階ごとに、互換の一致数・critical の緑・ベンチの pass 率とスコア・初期化の秒数を残す。
- **危険**
  - セッションを共有できないなら、パス単位でなく一括で切り替える。
  - `add_header X-Backend` のようにベンチへ見える形で目印を出す場合は、マニュアルが禁じる「ベンチの識別」に当たらないか、静的ファイル・応答の構造を変えていないかを確かめる（ログに出すだけにするのが安全）。
  - `location` の末尾のスラッシュなど、振り分けの誤りに気づきにくい。ログを切っていると振り分けの動作を確かめられない（ISUCON12 予選 daiju は、ロックの要る URI を別の台に寄せる試みがベンチを通らず、ログも切っていたため原因も確認できなかった）。
  - **1 つの点が大きく上がった直後に失格が続く例がある**。複数回流して pass 率を見てから残す。
  - 切り替えた後、旧サービスを `disable` して残す（戻せるように消さない）。新しいサービスは `enable` を忘れない（再起動後に動かない）。
- **出典**: `assets/nginx-switch.conf.example`、[daiju の ISUCON12 予選](https://zenn.dev/daiju/articles/165da7a5589434)。（4）。

### 動かす実装を 1 つに決める

- **効く条件**: 置き換え中で、元の実装と新しい実装が両方リポジトリにある。デプロイの道具・エージェントがどちらを見るか曖昧。
- **危険**: 二重の実装は、エージェントを別のコードへ導く。

## 全面インメモリ化への書き換え

DB を外して全部のデータをメモリに置く書き換え。点は大きく動くが、**再起動試験で落ちると 0 点**で、着手が遅いと完成しない。詳しい設計（無効化・永続化）は 08 章。ここでは判断の時刻と過去の実例を扱う。

### GO / NO-GO の判断

- **効く条件**: DB の往復・DB の CPU がボトルネックで、インデックス・N+1・キャッシュでも足りない。読みが書きより多い。
- **やり方**: 次の 3 つを、すべて満たすときだけ進める（チームの `isu-rewrite` の GO/NO-GO）。
  1. 外部仕様を読み切れた（全エンドポイントの入出力と副作用を書ける）。
  2. データがメモリに載る（DB のサイズ × ベンチ中の増加）。
  3. 整合性の要件を把握した（マニュアル）。
  進めるなら、**設計を先に出して**（メモリ上の構造・イベントの一覧・ロック粒度・再起動時の復旧）から実装する。判断は人間の責任者が出して、記録に残す。
- **確かめ方**: 仕様書・メモリ上の構造・イベントの一覧が、実装の前にある。
- **危険**: 仕様の読み残しがあると、書いた直後の読みが古くなる、権限の検査が抜ける、などで FAIL になる。

### 判断の時刻（実例から）

- **効く条件**: 全面インメモリ化を検討している。いつまでに決めればよいか。
- **やり方**: 次の実例から、**着手から完成・検証までの所要**を見積もる。

| 回・チーム | いつ・何を | 結果 |
| --- | --- | --- |
| ISUCON3 予選（methane。2013） | データがメモリに載ると見て、DB は書き込み専用にし、ログイン状態を考慮したページキャッシュを作った（序盤から設計） | 結果は出典に無い。本選は複数台なので、中継・RPC・PubSub の準備が要ると書く |
| ISUCON5 本選（fujiwara。2015） | 16:00 から飛び道具の実装に入り、時間内に動かせず、後日の修正で動いた | 失敗。「大きな変更は、実装と検証に残せる時間を見て絞る」 |
| ISUCON12 本選（NaruseJun。2022） | 13:50 にマスターのキャッシュ、15:20 に単一アプリのモードを環境変数で追加、16:15 に BAN データをメモリへ（単一アプリのモード）。感想戦でセッションを全部メモリに持ち、再起動用に JSON へ書き出し、書き込みを非同期にし | 競技の最終 341,258 点（優勝）。感想戦 691,921 点 |
| ISUCON13（NaruseJun。2023） | 11:00 台にタグ・ユーザー・UserModel をメモリへ、13:00 台にアイコンのハッシュ、15:00〜17:00 にライブストリームと NG ワードをメモリへ。DNS もアプリへ埋め込んだ | 最終 468,006 点（優勝）。17:00 以降のログ停止で 400k 超 |
| ISUCON14 本番（kawaemon と shun-shobon） | 椅子の総走行距離・現在位置・評価をグローバルな map に置いた。INSERT・UPDATE のクエリは変えていない | **データ保持違反で失格**（スコア順位は 37,127 点で全体 8 位）。原因は記事の時点で不明 |
| ISUCON14 感想戦（kawaemon。Rust） | 約 1 か月かけて DB をほぼ全廃。起動時に全行を読み、書き込みはキューにためて 500 行ごとに一括で書く | 850,573 点（公式の Go の最高 58,153 点とは条件が違う） |
| ISUCON14 感想戦（ponyo877。Go） | 全部の永続化処理を `sync.Map` へ。再起動対策は構想のみで未実装 | 感想戦の最高 864,990 点。**再起動試験なしの点で、本番用にならない**と本人が書く |

- **確かめ方**: 着手の時刻を決めたら、「ここまでに動かなければ捨てる」時刻（撤退の時刻）を一緒に決める。
- **危険**
  - 目安（チームの決まり）: **凍結に間に合わない大きな書き換えは始めない。** 全面の書き換えは、仕様の把握が済んだ序盤（午前〜昼）に決める。`isu-rewrite` は 12:00 までに判断する。
  - 点が大きく上がっても、再起動試験を通っていなければ点にならない。

### 永続化と再起動試験（書いたデータが残るか）

- **効く条件**: DB の書き込みを遅らせる・減らす、またはメモリを正にした。
- **やり方**
  - **SIGTERM で書き残しを流し切る**。`TimeoutStopSec` の中に終わらせる。永続の置き場は `/tmp` を避ける（再起動で消える）。ExecStop・ExecStart で書き出し・書き戻しをする案もある（ponyo877 の構想。ISUCON でしか通用しない手と本人が書く）。
  - `/initialize` で、メモリのキャッシュを破棄して DB の正から作り直す（独自の複製先も）。
  - 初期データから作った状態（元の画像の行・ファイル）を、更新で壊さない。
- **確かめ方**: **再起動試験を、ベンチを流した後に全台同時に行い、ベンチ中に書いたデータが残り、手作業なしでサービスが上がること**を確かめる（15 章）。整合性チェックでも確かめる。
- **危険**
  - **データ保持違反は失格。** ISUCON14 の本番では、2 人で参加したチームが、スコア順位で全体 8 位のままデータ保持違反で失格した。
  - クリーンな停止だけを前提にした永続化は、強制終了で失われる。再起動試験の方式（`reboot`・電源断）はその回のマニュアルで確かめる（出典未確認）。
  - DB の時計とアプリの時計を混ぜると、最後の書き込みの勝ちの比較がずれる。

## 書き換えの進め方（仕様→テスト→移植）

### 仕様書とテストを先に、移植は 1:1 で、高速化は別のコミットで

- **効く条件**: 置き換え・全面の書き換えを始めると決めた。
- **やり方**
  1. 仕様書（API の一覧・テーブル・主要フロー・整合性が要る箇所）を作る。**振る舞いの正はマニュアルと API の仕様書**で、点になる操作ごとに「何を返せば点か」を先に書く（雛形 ）。初期実装は、仕様に書いていない所だけ倣う。推測で埋めない。
  2. 互換テストと critical のテストを作る（上の節）。
  3. **まず同じ結果を返すだけの 1:1 の移植**。クエリ・トランザクションの境界・ロックの範囲・応答の形を変えない。スキーマと初期データは変えない。
  4. 互換が通ってから、計測して高速化する。**動かすための移植と性能改善は、コミットを分ける**（後で比べるときの基準がぼやけるため）。
  6. **リファクタを先に**（型・DB 呼び出しの集約）。そうしないと、最適化がコードを変えにくくする（kawaemon）。
- **確かめ方**: 互換テストの一致数、critical の緑、初期化の秒数、失格条件。
- **危険**: 最適化と移植を同じコミットに入れると、退行の原因が分からなくなる。デプロイの道具が、実際に新しいコードを反映しているか確かめる（ISUCON14 のあるチームは、デプロイスクリプトがアプリを反映しておらず、点の伸びはインデックスだけによるものだった）。

### 仕様から作り直す（継ぎ足しをやめる）

- **効く条件**: 仕様の振る舞いとアプリの特性が書けた。初期実装に継ぎ足していて、点を左右する決まり（占有・運賃・ボーナスの条件など）が複数の場所に散っている。
- **やり方**
  - 12:00 の構成の判断で、「継ぎ足す」と並べて正式な選択肢にする（`docs/strategy.md`）。
  - **判断の前に、設計を変える問いに答え切る**（雛形  の 7 節）: 何を返せば点か・ボーナスと失格 / 点の上限は何で決まるか（集中させる条件・こちらで選べる値）/ 何がどれだけ読まれ書かれるか・熱いデータの大きさ / 再起動後に残すものと初期化で作り直すもの / 外部サービスの振る舞いと制約 / 取りこぼしの内訳。「できるだけ」ではなく、この一覧を埋め切るまで。11:30〜12:00 で区切る。
  - 初期実装は振る舞いの正にはしないが、計測の道具として使う。負荷をかけないと出ない答え（集中・取りこぼし・ボーナスの取れ方）は、初期実装のままベンチと実験で取る。
  - 判断には、答えた問い・答えられなかった問い・その仮置き（作り直した後の確かめ方）を出す。
  - 層は薄く: HTTP の入出力（応答の互換）/ 決まり（純粋な関数。仕様から書いたテスト付き）/ データ（メモリの状態と DB への永続化）。インターフェース・リポジトリの層を重ねない。
  - データの持ち方は、リクエストの特性（何がどれだけ読まれ、何が書かれるか）から決める。メモリに持つもの・DB に永続化するもの・initialize で作り直すものを分ける。
  - モジュールの境目を subagent に渡す単位にする（決まり・データ・HTTP の 3 本を並列に）。互換テストの基準は仕様。
  - 締め切りを決める（例: 15:00 に競技サーバーで動いていなければ、継ぎ足しの版に戻す）。継ぎ足しの版はいつでも戻せるようにしておく。
- **確かめ方**: 作り直した版で再起動試験を 1 回通す。スコアの帳簿の取りこぼし・ボーナスの件数を、継ぎ足しの版と並べる。
- **実例（2026-11-02 の練習、ISUCON9 本戦）**: 継ぎ足しで 4 時間進めて 124,567 点。延長戦で仕様から作り直し、仕様の書き出し 8 分、subagent 3 本を並列にして 15 分で初めて通った。同じ予約可能日数（118 日）で比べると、継ぎ足しの版 約 379k に対し、作り直した版 456〜482k（+25% 前後）。作り直す途中で、点の上限の正体（予約が連休に集中すること）が見えた。点の伸びの大半は日数の選び方で、作り直しの寄与は 2 割程度。上限の正体を知らないまま作り直しを始めていた。先に問いの一覧を埋めていれば、日数の選び方も作り直しの設計に入っていた（作り直しの費用は 15 分と小さく、判断の質を決めるのは情報のほう）。
- **危険**: 作り直しの費用は agent がいれば小さいが、仕様の読み残しは FAIL になる。仕様に書いていない所は初期実装に倣い、どちらを取ったかを記録に残す。

### ビルドを軽く保つ（Rust への置き換え）

- **効く条件**: Rust へ置き換えると、ビルドが数分かかり、全員が同じマシンで順番待ちになる。
- **やり方**: 開発・e2e 用は LTO を切って `codegen-units` を増やす。依存の層を先に作る。同じ入力ならビルドし直さない。**ビルドはまとめて直列に**。詳細は 09 章。
- **確かめ方**: ビルド時間、手元の load average。
- **危険**: 本番のビルド設定（LTO など）は変えないので、e2e で試すバイナリは最適化が本番と違う。

## よくある失敗

| 失敗 | 実例 | 対策 |
| --- | --- | --- |
| 再起動試験で落ちる | ISUCON14 本番の kawaemon と shun-shobon（データ保持違反で失格）。ponyo877 の感想戦（永続化は未実装） | 書き込みを DB へ残す。再起動試験を、ベンチ後に全台同時で行う |
| 二重の実装が残る | INUCON の ISUNARABE。ansible が Go の実装を前提にして、移植がデプロイの前に要った | 作業先とデプロイ元を 1 つに決める |
| 最適化を先にして作り直す | kawaemon の感想戦で、リファクタ前の最適化に 3 日使い、コードをリセットした | まずリファクタと DB の使われ方の整理 |
| 言語に慣れていない | ISUCON12 の dyoshikawa は、途中で Ruby から Go に替えて最終 3,160 点 | 慣れた言語で。替えるなら、事前に練習する |
| 移植が正しいか確かめない | ISUCON13 の myuon は、DB エラーで画像のフォールバックを返し、仕様違反の FAIL で約 80,000 点が約 10,000 点に | 互換テストと critical のテストを、切り替えの前に |
| 目印をベンチに見える形で出す | （一般的な危険。手元の記録は無い） | 切り替えの目印はログだけに出す。マニュアルの禁止事項を確かめる |
