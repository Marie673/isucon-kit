# 作戦 REV 4: 何を回すかを決める仕組みを、1 本のループで持つ

## 版の変更点

- **REV 3**: 「方向を決める層」を一番上に置いた。
- **REV 4**（2026-11-01）: 役を分けるのをやめ、**メインエージェント 1 本**（設計とベンチと小さな実装を持つ agent）に畳んだ。subagent は、コンテキストで切れる仕事にだけ、道具のように呼ぶ。
  - 根拠は 2 つ。
  - 1 つ目は Anthropic の記事「[Building agents: When to fold subagents into your main agent loop](https://claude.com/ja/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)」（2026-10-22）。要点は 3 つある。
    - 多くの場合、1 本のループに skill（手順）と道具（守る条件）を足す形のほうが、subagent に分ける形より品質が高く、速い。
    - 分けるなら、問題の種類ではなくコンテキストで切る。
    - 守る条件は、プロンプトではなく道具の側で拒否して返す。

|---|---|
| 構成が組織図の写しになる | issuer・delivery・Grafana・monitor・ベンチの 3 役・実行役 20 体 |
| 渡すたびに詳細が欠ける（伝言ゲーム） | 依頼の中継に `bq` が要った。1 件の依頼に 22 件・8,814 字が統合され、80 分着手されなかった |
| コンテキストの膨らみ | 常駐役のコンテキストが 70〜90% になり、1 ターンが遅くなった |
| ルールの継ぎ足しが衝突する | AGENTS.md が 273 行になり、時刻つきの例外が積み重なった |
| 構造そのものが遅延を生む | 依頼から着手まで約 25 分かかった。13 時台は main が 5 回、反映できない状態になった |
| 方向を決める知識が誰のコンテキストにも揃わない | スコアの式・ピークの CPU・利用者の行動の連鎖は、どの役も丸ごとは持っておらず、どれも競技の後に分かった |

## 全体の形

```
 メインエージェント（agent 1 本。人間には聞かない。main の canonical checkout）
   design.md の A（何を返せば点か。正は仕様）
   design.md の B ─┐
                   ├─▶ design.md の D ─▶ 作戦ボード（docs/README.md）のボトルネック表─▶ 今のボトルネックを 1 つ
   design.md の C ─┘        ▲                                         │
                            │                                         ▼
        傾向を掴む実験 ──────┘     小さな変更は自分で入れる ─▶ bin/isu-bench（ロック→反映→ベンチ→窓の要約）
                                   大きい・並列にできる仕事は subagent に ─▶ ブランチと短い報告を受け取り、取り込む
                                                                           │
                                   結果（ぶれの幅と比べて）をボトルネック表へ ◀───┘
```

- 方向（4 枚の文書）・反映とベンチ・結果の読み取りを、同じコンテキストが持つ。要約を渡す段が無い。
- 4 枚の文書は `docs/` に置く。ループが compact しても、ここを読み直せば続けられる（記事の「必要なときだけ読む参照資料」）。
- 序盤のベンチは、改善の確認ではなく、問いに答える実験に使う。最終のスコアは最後のベンチで決まり、途中のベンチのスコアは残らない。
- ボトルネック表に載った仕事だけを回す。ボトルネック表に無い改善は、手が空いたときだけ。

## 方向の決まり

1. **最初にアプリの特性とスコアのモデルを書く。** 実装の改善より先。見た目の似たサービス（SNS・EC など）の負荷を思い浮かべず、利用者がいつ・何をきっかけに・一斉に動くかを書く。モデルが無いうちに出た改善案は、ボトルネック表の「保留」に置く。
2. **傾向は実験で掴む。** 増える条件・上限・どのボトルネックがスコアに効くかが分からなければ、改善を積む前に、ボトルネックを一時的に外したベンチで確かめる。競技サーバーは資源を足せない（スペックアップは失格）ので、引く・足す（遅延）・寄せるで代える。
3. **ボトルネックは 1 つに絞る。** ボトルネック表の一番上を「今のボトルネック」とし、根拠の数字（窓の要約・プロファイル・スコアの帳簿）を必ず添える。
4. **スコアの帳簿で見る。** API の平均レイテンシではなく、「どこでスコアを落としたか」（地域 × 日 × 理由）で見る。帳簿を出すスクリプトはモデルを書いた直後に作る。
5. **構成は紙の上の計算で決める。** 最大の地域の最終日のピークで、サーバーごとの CPU が足りるかを計算する。足りないなら、設定の調整ではなく構成を変える。
0. **考え方を先に置く。** 見る → 説明する → 理屈で形を決める（`template/AGENTS.md` の「考え方」）。決まりや道具を足すより、この流れで考えられるようにする。
6. **スコアの目標を持たず、ボトルネックをなくし続ける。** 順位表の点や目標のスコアを書いて持たない。凍結までボトルネックを取り続け、効く項を止めているものを選ぶ。1 本のスコアで手をやめない。
7. **指示はモデルの言葉で出す。** 「スコアを上げろ」ではなく「投稿直後のフィードが空の人を 5 割から 1 割に」「新しい利用者の動線を 9 秒の窓の中で終える人を 9 割に」。届かない数字の目標（`/goal` を含む）は出さない。

## 流れの決まり

1. **ぶれの幅を知ってから比べる。** 幅より小さい差は「差なし」。採否が割れる変更は、同じ設定と交互に 2 本ずつ流してから決める（`tools/noise`）。
2. **構成・設定の切り替えは単独で反映する。** コードの改善はまとめてよいが、比べたい変更は 1 つずつ。
3. **フラグは台帳に載せてから入れる。** 根拠と消す条件のないフラグは入れない（`tools/flags`）。
4. **反映 → ベンチ → 要約を 1 コマンドで。** `bin/isu-bench` を使い、窓の要約（`tools/bench-window`）をその要約に足す。
5. **判断に要る数字は 1 か所に集める。** スコア・スコアの式の項・取りこぼし・今のボトルネック・今の判断を考え直す条件を、作戦ボード（`docs/README.md`）の判断の数字に置き、ベンチのたびに最初に直す。ほかの文書は根拠を引く場所。数字が散ると、撤回の条件が満たされても気づかない。
6. **守る条件は道具に持たせる。** 「反映は 1 本ずつ」「宣言したパスの外を触らない」「台帳に無いフラグ」は、プロンプトで頼まず、道具が拒否して理由を返す形にする（`isu-bench` のロック、`isu-task`、`tools/flags lint`）。新しい決まりを AGENTS.md に足したくなったら、先に道具で解けないかを考える。

## ループの決まり

### メインエージェント

- **1 本だけ。** main の canonical checkout で動く。skill `main-loop`。
- **人間に聞かない。** 質問・承認の依頼・判断の依頼をせず、区切りの報告も記録に書くだけで返事を待たない。構成の判断・危険のある施策も自分で決め、`docs/DECISIONS.md` に根拠・確かめ方・撤回の条件を書く。ベンチは最初の 1 本から自分で流す（ポータルなら Chrome の道具）。人間は観察する側で、入力が届けば情報として取り込む（人間の指示 2026-11-03。skill `main-loop` の「聞かずに決める」）。
- 持つもの: 4 枚の文書とボトルネック表の順番、反映とベンチ（`bin/isu-bench`）、結果の読み取り、main への取り込み。
- **小さな変更は自分で入れる。** 目安は、1 つのボトルネックの行に効き、数十行・1〜2 ファイルで、すぐ確かめられるもの（インデックス、設定、N+1 の 1 か所）。subagent に渡すより速く、報告で詳細が欠けない。
- **main に書くのはメインエージェントだけ。** subagent と別のエージェントはブランチを返し、メインエージェントが差分を読んで取り込む。書き手を 1 つにすると、壊れた main が反映を止めることが減る。
- コンテキストは区切りで手動で compact する。区切りは構成の判断の後・前提の見直しの前・17:00 と、使用量が 60% を超えた区切り。残すものは、自分の役と skill、進行中の件、次の一手、動かしているバックグラウンドの処理。

### subagent（道具として呼ぶ）

記事の基準に合う 3 種類の仕事だけに使う。手順は skill `delegate`。

| 種類 | 例 | 返させるもの |
|---|---|---|
| 並列にできる独立した実装 | 別々のエンドポイントの言語の置き換え、ボトルネック表の別の行で触るファイルが重ならない 2 件 | ブランチ名、20 行以内の要約、テストの結果 |
| コンテキストを混ぜたくない調べもの | マニュアルの該当の節、capture の集計、チューニングマニュアルの該当の章、コードの呼び出し関係 | 答えと出典（ファイル:行、節） |
| 結果だけを見る検証 | 互換の突き合わせ、ルール違反の点検、critical のテスト、差分のレビュー | 合否と、落ちた箇所 |

- 依頼はコンテキストで切る。「この行の、このファイルを、こう変え、こう確かめる」まで書く。問題の種類（「DB 担当」「画像担当」）で常駐させない。
- subagent は main に書かない。反映もベンチも流さない。

### 別のエージェント（人間が別に持つループ）

- 0〜2 本。人間 2 人目・3 人目が、メインエージェントとコンテキストを共有しなくてよい長い仕事（言語の置き換え・構成の作り直し）を持つときだけ、worktree で動かす。
- ボトルネック表の行を 1 つ受け持ち、終わったらブランチをメインエージェントに返す。ボトルネック表の順番は変えない。

## 役

| 役 | 数 | やること | skill |
|---|---|---|---|
| メインエージェント | agent 1（人間は観察） | 4 枚とボトルネック表、反映とベンチ、小さな実装、main への取り込み、subagent の呼び出し | `main-loop`、`delegate`、`app-profile`、`score-model`、`capacity-plan`、`probe-experiments`、`experiment-rules` |
| subagent | 同時に 0〜4 | メインエージェントが渡した 1 件を、捨てられるコンテキストで片付けて短く返す | `isu-loop` の 0〜5（ベンチの依頼はしない） |
| 別のエージェント | 0〜2 | 人間が持つ長い仕事。終わったらブランチを返す | メインエージェントと同じ文書を読む |

- 起票役が別にいると、ボトルネック表と関係なく課題が積まれる。
- 配る役・ベンチの役が別にいると、要約を渡すたびに詳細が欠け、待ちが生まれる。
- 監視は道具で持つ（`isu-bench` の要約、`isu-lock status`）。

## 体制を変えるときの確かめ方

記事の「先に評価を作り、一度に 1 つ変え、複数回走らせる」に従う。

- 物差しは過去問の通し。同じ問題で、メインエージェントだけの通しと、subagent を増やした通しを比べる。
- 比べる数字は 3 つ。スコア、ボトルネックを当てた時刻、変更が main に入ってからベンチの結果がボトルネック表に載るまでの時間。
- 1 回の通しで変えるのは 1 つ（subagent の数、別のエージェントの有無など）。

- 道具（`tools/`）を通しで動かしておく。
