# 14 ベンチマーカーと配点

**当日のマニュアル・レギュレーションが常に優先する。** 配点・負荷の増え方・失格条件・初期化の制限時間は、回ごとに違う。この章の過去の例は「読み方の練習」であり、次の回に当てはまる保証はない。

## この章で扱う範囲

- スコアの式、配点の上限、減点と FAIL の条件の読み方。
- 負荷の増え方（応答を待って次を送る型、エラーや遅い応答で負荷が増えない仕掛け、タイムアウト）。
- ベンチの利用者の行動の読み方。
- ベンチの出力（ポータルの結果）からの読み取り方。
- 初期化（initialize）の役割と制限時間。
- 過去の回の例。

扱わないもの: 点を上げる個別の手（各層の章）、終盤の再起動試験と最終ベンチの選び方（[15 章](15-endgame.md)）、計測の方法（[01 章](01-measurement.md)）。

## 1. スコアの式と上限

### スコアの式を、1 人（1 件）あたりの上限まで落として書く

- **効く条件**: 配点表の最大値（10 点や 20 点）に注意が引かれる。どの API を速くすれば点が増えるか分からない。
- **やり方**:
  1. マニュアルの配点表を、API ごとの点・1 人あたり（または 1 窓あたり）の上限・倍率に分けて書く。
  2. 1 人（1 件）が取れる最大の点を足し上げる。
  3. 人数（件数）の増え方を掛けて、理論上の上限を出す。
  4. 順位表の上位の点と比べる。上限を超える点が出たら、前提のどれかが違う。
- **危険**:
  - 「5 回まで」の単位（窓ごとか、走行全体か）がマニュアルに無いことがある。質問する価値がある。

### 回数ではなく「成功の件数」で数える点を見分ける

- **効く条件**: HTTP のリクエスト数を増やしても点が増えない。API を速くしたのに点が伸びない。
- **やり方**: 点が「HTTP の成功数」か「ベンチが活動の成功を確かめて加点した回数」かを読む。
  - ISUCON11 予選: 加点はコンディションを**まだ見ていない**ものを見た回数と、グラフの確認。同じものを何度見ても増えない。
  - ISUCON12 予選: エンドポイントごとの固定点（1 点または 10 点）。成功するたびに加点。
  - ISUCON10 予選: イスの購入件数 + 物件の資料請求件数。ISUCON13: 投げ銭の金額の合計。ISUCON14: 移動距離（乗車前 × 0.1、乗車中 × 1）とライド完了数 × 5。
- **確かめ方**: 変更の前後で、点と「点に結びつく API の成功件数」を並べる。API の速さが上がっても点が動かないなら、点を止めている別の処理を探す。
- **危険**: 点の源泉でない処理を磨いて時間を使う。
- **出典**: [ISUCON11 予選のマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/manual.md)、[ISUCON14 のマニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)、[ISUCON12 予選のマニュアル](https://gist.github.com/mackee/4320c18919c8f6f1867849378a17e651)、[ISUCON10 予選のマニュアル](https://gist.github.com/progfay/25edb2a9ede4ca478cb3e2422f1f12f6)、[ISUCON13 の当日マニュアル](https://github.com/isucon/isucon13/blob/main/docs/cautionary_note.md)。

### 倍率・ボーナスは、先に使える条件を調べる

- **効く条件**: 配点に倍率やボーナスがある。
- **やり方**:
  - ISUCON10 本選: `(仮想選手スコア × 大会規模ボーナス) + 仮想オーディエンススコア − 減点`。ボーナスは参加した仮想選手の数で 1.0〜2.0（60 人刻み）。
  - ISUCON9 本選: エンドポイントごとの点 × 成功数 + ボーナス（仮予約 10 点、隣り合う席で 10〜25 点）− 減点。
  - ISUCON9 予選: `POST /initialize` の戻り値の `campaign`（0〜4）で、同時アクセスする利用者の数が変わる。
- **危険**: 倍率の条件（ボーナスのために人数を増やす）が、他の処理の負荷を上げる。
- **出典**: [ISUCON10 本選のマニュアル](https://github.com/isucon/isucon10-final/blob/master/docs/manual.md)、[ISUCON9 本選のマニュアル](https://github.com/isucon/isucon9-final/blob/master/docs/MANUAL.md)、[ISUCON9 予選のマニュアル](https://github.com/isucon/isucon9-qualify/blob/master/docs/manual.md)。

## 2. 負荷の増え方

ベンチマーカーは、利用者の動きを模したプログラム。「どう負荷を上げるか」はマニュアルに書かれないことが多い。次の 3 つの型を知っておくと、ベンチの出力から読み取れる。

| 型 | 中身 | 例 |
| --- | --- | --- |
| 固定で降り注ぐ型 | 応答に関係なく、決まった頻度でリクエストが来る | ISUCON11 予選の ISU のコンディション送信、ISUCON10 予選の Bot、ISUCON13 の DNS 水責め（ratelimit つき） |

以下、この 3 つの読み方を項目に分ける。

### 「成功すると負荷が増える」型を見分ける

- **効く条件**: 速くしたのに点が伸びない。ある時点から利用者（並列数）が増えない。ベンチの出力に「利用者が増えた」「離脱した」の言葉が出る。
- **やり方**: 次の根拠を探す。
  - **ISUCON12 予選**: ベンチのソースに「リーダーボードの表示に 1.2 秒以上 3 回かかったら参加者が離脱する」という処理がある。ベンチのログに「leaderboard の表示に 1 秒以上かかったため N 人の参加者が離脱しました」「参加者が N 人増えました」が出る。
  - **ISUCON12 本選**: 講評は、リクエストを捌くと並列数が段階的に上がる設計だと書く。
  - **ISUCON11 予選**: トレンドが改善されるとユーザーと ISU が増え、リクエスト数が急増する。捌けないと点が下がる。遅いと閲覧できるページ数が減る。
  - **ISUCON10 本選**: 仮想負荷走行が 1 回実行されるたびに、仮想オーディエンスが 1 人増える。
  - **ISUCON9 本選**: `available_days` を月単位で上げて負荷を増やす。いきなり大きくすると、捌ききれずタイムアウトで減点される。連休・五輪の期間は負荷が増える。
  - **ISUCON14**: ユーザーは評価に応じて増える（個人評価が高ければ招待、地域の平均評価が高ければ口コミ）。オーナーは利益が見込めれば椅子を追加する。
- **確かめ方**:
  - 人数が増えない走行と増える走行で、応答時間（1 秒超の割合）・エラー・タイムアウトを比べる。
- **危険**:
  - 人数が上限に届いた後の伸びしろは、1 人あたりの操作だけになる。上限が不明のまま、台の処理量を増やすことに時間を使うと外れる。
  - 増員の判定式はマニュアルに無いことが多い。1 本の走行で確定させず、複数の走行の表で読む。
- **出典**: [ISUCON12 予選のベンチのソース](https://github.com/isucon/isucon12-qualify/blob/main/bench/scenario_player.go)（離脱の処理）・[scenario.go](https://github.com/isucon/isucon12-qualify/blob/main/bench/scenario.go)、各回の講評（[ISUCON12 本選](https://isucon.net/archives/56959385.html)、[ISUCON11 予選](https://isucon.net/archives/56044867.html)、[ISUCON10 本選](https://isucon.net/archives/55140539.html)、[ISUCON9 本選](https://isucon.net/archives/53916974.html)、[ISUCON14](https://isucon.net/archives/58869617.html)）。

### 遅い応答・エラーで負荷が増えない（応答待ち型の落とし穴）

- **効く条件**: 台の CPU が空いているのに点が伸びない。ベンチの 1 本の中で、後半のほうが利用者が少ない。
- **やり方**: 次の「ベンチ側の待ち・離脱」を探す。
  - ISUCON7 本選: 状態を返す API に 1 秒以内の応答条件があり、遅いと負荷が増えなかった（加算の API を速くしても、状態計算を直すまで伸びなかった）。
  - ISUCON9 予選: ログインの bcrypt を sleep で遅らせると、人気者出品に必要な人数が集まらず、点が伸びない（講評）。
  - ISUCON11 本選: 履修登録・課題提出は科目ごとに待機するので、遅いエンドポイントが 1 つあると全員が待たされる。参考実装は成績取得でタイムアウトが頻発し、タイムアウトした学生は 10 秒スリープする。
- **確かめ方**:
  - ベンチ中の台の CPU を見る（[01 章](01-measurement.md)の山の窓）。走行の大半で空いていて、最後の山だけ張り付くなら、負荷が山に集中している。空いている間に負荷が来ていない理由を、ベンチの利用者の待ち（`sleep`・次の行動の条件）から探す。
  - 遅い応答の上位（`p99`・最大）と、`499`・`5xx`・タイムアウトの件数を、alp で時刻順に見る。
- **危険**: **負荷が増えない原因が、サーバーの遅さではなく、ベンチ側の待ち（利用者の行動の条件）のこともある。** 条件を満たさないと次に進まない動線がある。
- **出典**: 実例 ISUCON7 本選。[ISUCON9 予選の講評](https://isucon.net/archives/53789931.html)、[ISUCON11 本選の講評](https://isucon.net/archives/56163308.html)。

### エラーで負荷が打ち切られる型（ワーニング・減点の累積）

- **効く条件**: 走行の途中で FAIL になる。ベンチの出力に「打ち切り」が出る。
- **やり方**: 打ち切りの条件を、マニュアルから表にする。
  - ISUCON14: 負荷走行中にワーニングが 200 件以上、またはクリティカルエラーで打ち切って FAIL。
  - ISUCON12 予選: エラー 1 個につき 1%、critical は 10% の減点。減点が 100% になった時点で打ち切って FAIL（例: critical 7 個とそれ以外 30 個）。
  - ISUCON11 予選: HTTP の誤りが 100 回で FAIL。
  - ISUCON11 本選・ISUCON10 本選: HTTP の誤りが 100 回を超えたら FAIL。ISUCON10 予選: 10 回以上で失格。ISUCON9 予選: 10 回以上で失格。ISUCON9 本選: 1000 回で失格。
- **確かめ方**: ベンチの出力の件数と、打ち切りの閾値を比べる。メッセージが同じ内容のものを 1 つにまとめる回があり、表示の数とエラー数は一致しないことがある（ISUCON9 のマニュアル）。
- **危険**: 打ち切りの閾値が低い（ISUCON10 予選の 10 回）と、整合性を壊す変更 1 つで走行が FAIL になる。
- **出典**: 各回のマニュアル（下の「過去の回の例」の出典）。

### 固定で降り注ぐ負荷（Bot・DNS・ISU のデータ送信）

- **効く条件**: 点にならない種類のリクエストが、台の CPU を食っている。
- **やり方**:
  - ISUCON10 予選: 初期はほとんど来ない Bot のリクエストが、負荷レベルが上がると増える。マニュアルの正規表現に一致するリクエストは 503 で返してよい（講評）。
  - ISUCON11 予選: ISU は仮想時間でコンディションを送り続ける。`POST /api/condition/:jia_isu_uuid` は、誤りもタイムアウト（100ms）も減点・FAIL にならない。
  - ISUCON13: DNS 水責め（ランダムなサブドメインの大量の名前解決）が、ratelimit つきで行われる。
- **確かめ方**: alp で、点に結びつかない URL の件数と合計時間を見る。
- **危険**:
  - ベンチを見分けて違う結果を返すことは、失格になりうる。User-Agent などで Bot を判定する手が許されるのは、マニュアルが明示した場合だけ。
- **出典**: [ISUCON10 予選のマニュアル](https://gist.github.com/progfay/25edb2a9ede4ca478cb3e2422f1f12f6)・[講評](https://isucon.net/archives/55025156.html)、[ISUCON11 予選のマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/manual.md)、[ISUCON13 の講評](https://isucon.net/archives/58001272.html)。

## 3. タイムアウト

### タイムアウトの値を表にして、アプリの最悪の応答と比べる

- **効く条件**: タイムアウトで減点・FAIL が出る。アプリの最悪の応答時間が分からない。
- **やり方**: マニュアルのタイムアウトを、エンドポイント別に表にする。同じ回でも API ごとに桁が違う。
  | 回 | タイムアウト |
  | --- | --- |
  | ISUCON9 予選 | `POST /initialize` 20 秒。アプリの応答が 10 秒を超えると失格（制約事項に記載） |
  | ISUCON10 本選 | initialize 20 秒。一部の API は 2 秒、それ以外は 10 秒（それを超えると減点） |
  | ISUCON11 予選 | initialize 20 秒、`POST /api/condition/:id` 100 ミリ秒、それ以外 1 秒 |
  | ISUCON11 本選 | initialize 20 秒、それ以外 5 秒 |
  | ISUCON13 | initialize 42 秒、整合性チェック 20 秒、負荷テスト中 20 秒、最終チェック 10 秒 |
  | ISUCON14 | initialize 30 秒、通知の 2 本 60 秒、それ以外 10 秒（初期化の各 POST は 10 秒、全体 20 秒） |
- **確かめ方**: alp の `max`・`p99` を、タイムアウトの値と並べる。最悪の応答が閾値に近い API を探す。
- **危険**:
  - **負荷テストの終了時に切断されたリクエストは、スコアにも検証にも影響しない**（ISUCON11 予選・ISUCON13・ISUCON14 のマニュアル。nginx のアクセスログに 499 が出るが減点対象外、と書く回もある。ISUCON9）。499 を見て慌てない。
  - ISUCON14 は、負荷テスト終了時の決済処理が 5 秒以内に終わらないと、金額の不一致で FAIL。
  - ISUCON11 本選の「リトライ処理（10 秒）」は、加点・減点の対象外。
- **出典**: 各回のマニュアル（下の「過去の回の例」の出典）。

## 4. ベンチの利用者の行動

### 利用者の動線を、次に進む条件つきで書く

- **効く条件**: どの API が点に効くか、どの API を速くすれば次の操作が増えるか分からない。
- **やり方**:
  1. マニュアルの「ベンチマーカーの動作」と配点表から、利用者の操作の列を書く。
  2. 各段に「次に進む条件」を書く（友達の投稿があること、窓の中に終わること、前のレスポンスが来ること）。
  3. 実際のリクエストを capture（`day0-capture` の手順。出題内容を含むのでコミットしない）して、列を確かめる。
  4. アクセスログを利用者 ID ごとに並べて、1 人の操作の列として読む。
- **危険**: ベンチの利用者は、ブラウザと違う動きをする（ISUCON9 予選のマニュアルは「ベンチマーカーとブラウザの挙動に差異がある場合、ベンチマーカーの挙動を正とする」と書く）。仕様書ではなく、ベンチのリクエストを見る。
- **出典**: 2 節、[ISUCON9 予選のマニュアル](https://github.com/isucon/isucon9-qualify/blob/master/docs/manual.md)。

### ベンチの時間（仮想時間・tick・窓）を知る

- **効く条件**: ベンチの 1 本は 60 秒（多くの回）でも、その中に「日」や「窓」がある。応答の目標がベンチの時間に対して決まっている。
- **やり方**:
  - ISUCON11 予選: 現実の 1 秒がベンチ上の 30,000 秒（仮想時間）。
  - ISUCON14: ベンチ内の世界は 30ms を 1 tick として動き、全エンドポイントが 30ms 以内に応答するのが理想（講評）。初期実装の通知は 30ms 間隔のポーリングだった。
- **確かめ方**: ベンチの出力・アクセスログから、窓の長さ・山の間隔を測る。
- **危険**: 窓より応答が遅いと、窓の中に操作が終わらず、次の日の人数が増えない。
- **出典**: [ISUCON11 予選のマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/manual.md)、[ISUCON14 の講評](https://isucon.net/archives/58869617.html)。

## 5. 減点と FAIL

### 減点（直接）と FAIL（走行が 0 点）と失格（チームの最終スコアなし）を分ける

- **効く条件**: 「エラーが出たら点が下がるのか、0 点になるのか」が分からない。
- **やり方**: マニュアルの用語を 3 つに分けて読む。
  | 用語 | 意味 |
  | --- | --- |
  | 減点 | その走行の点が下がる。FAIL にはならない（回による） |
  | FAIL（失敗） | その走行は 0 点。最終スコアに使われる走行が FAIL だと、最終スコアが無い（回による） |
  | 失格 | 追試・禁止事項違反で、チームの最終スコアが無くなる |
- **危険**: **減点がない回でも、エラーは点を落とす**。エラーになった操作は加点されないうえ、critical や警告の累積で FAIL になる。減点の有無で「エラーを許容してよい」と読まない。
- **出典**: 各回のマニュアル（下の「過去の回の例」の出典）。

### critical error と整合性チェックを、テストにする

- **効く条件**: 失敗の原因が、高速化の変更（キャッシュ・非同期・分割）で生まれた整合性の崩れ。走行が間欠的に FAIL になる。
- **やり方**: マニュアルの critical の一覧から、テストケースを作る。
  - ISUCON14: ユーザー・椅子が想定外の通知を受ける、ライドの想定外の状態遷移、評価済みなのに支払いがない、決済サーバーに誤った支払いを要求する、など。
  - ISUCON12 予選: テナント追加・大会追加・スコア入稿・大会終了・選手失格の API と、失格済みの選手の閲覧が critical。反映に最大 3 秒の猶予があるエンドポイントがある。
  - ISUCON10 予選: 致命的なエラー（例: CSV 入稿の失敗・タイムアウト）は 1 回で失格。
  - ISUCON9 本選: 同一座席の二重発券など。
- **確かめ方**: 変更ごとに critical のテストを回す。ベンチ 1 本が通っても、間欠的な失敗は 1 本では出ない。同時実行・繰り返しで確かめる。
- **危険**: 高速化の定番（メモリキャッシュ、書き込みの遅延、読み取りの分散）は、反映の猶予が無い API で整合性を壊す。猶予（3 秒・5 秒）が書かれている API だけが、遅延を許される。
- **出典**: [ISUCON14 のマニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)、[ISUCON12 予選のマニュアル](https://gist.github.com/mackee/4320c18919c8f6f1867849378a17e651)、[ISUCON10 予選のマニュアル](https://gist.github.com/progfay/25edb2a9ede4ca478cb3e2422f1f12f6)、[ISUCON9 本選のマニュアル](https://github.com/isucon/isucon9-final/blob/master/docs/MANUAL.md)。

## 6. 初期化（initialize）

### initialize の役割: 外から見える状態を、ベンチが想定する初期状態へ戻す

- **効く条件**: スキーマ・データ構造・キャッシュを変えた。初期化が失敗する、遅い、整合性チェックが落ちる。
- **やり方**: マニュアルの記述を読む。役割はどの回も同じで、DB（とキャッシュ・外部の状態）を、ベンチが期待する状態に戻す。
  - ISUCON11 予選: データベースを初期状態に戻し、ベンチマーカーが要求する範囲の整合性を保証する。処理やデータ構造を変えたら、この内容も漏れなく提供する。
  - ISUCON12 予選の講評: ベンチ開始時に呼ばれ、外部から観測できる状態を初期状態に戻す。
  - ISUCON9 予選のように、応答の値（キャンペーン率）が負荷に影響する回がある。
- **確かめ方**: 初期化後に、ベンチの整合性チェックが通ること。自分で追加したキャッシュ・複製先・メモリの状態が、initialize で初期状態に戻ること。
- **危険**:
  - **初期化で作り直さないキャッシュは、前の走行の状態を持ち越して、整合性チェックを壊す。**
  - 逆に、**initialize のときだけ埋めるキャッシュは、再起動後に空になる**（ISUCON10 本選で、コンテスト情報を initialize 時だけキャッシュしていて、再起動後のブラウザ操作でエラーになった。筆者はこれが失格の原因と推測している。実例）。キャッシュミス時の DB フォールバックを設ける。
  - 初期化に失敗すると、走行は即 FAIL（ほとんどの回）。
- **出典**: [ISUCON11 予選のマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/manual.md)、[ISUCON12 予選の講評](https://isucon.net/archives/56850281.html)、[ISUCON9 予選のマニュアル](https://github.com/isucon/isucon9-qualify/blob/master/docs/manual.md)。

### initialize の時間制限

- **効く条件**: スキーマを変えた・データを増やした・外部のファイルを作り直した後で、初期化が遅くなる。
- **やり方**: マニュアルの制限を、回ごとに確かめる。
  | 回 | 制限 |
  | --- | --- |
  | ISUCON9 予選・本選 | 20 秒 |
  | ISUCON10 予選 | 30 秒（超えると失格・0 点） |
  | ISUCON10 本選・ISUCON11 本選 | 20 秒を 2 回（互換性チェックの前後で 2 回呼ぶ） |
  | ISUCON12 予選 | 30 秒 |
  | ISUCON13 | 42 秒 |
  | ISUCON14 | 30 秒 |
- **確かめ方**: 初期化の所要を、変更のたびに測る。**制限の半分以内**を目安にする（ぶれと、本番のデータの違いのため）。
- **危険**:
  - ISUCON12 予選の講評: MySQL へ移したとき、`mysqldump` による論理バックアップの復元では 30 秒に収まらず、データディレクトリのコピーなどの方法が取られた。SQLite 版は単なるファイルのコピーで復元していた。
  - ISUCON12 予選: SQLite の各ファイルの全テーブルを読み直して一括挿入する初期化を試したところ、約 33 秒で制限（30 秒）を超え、撤回した。
  - **初期化が長くても、負荷テストの時間は削られない**。縮める価値は、制限の余裕と失敗しないことにある。初期化は配点に入らない。
  - ISUCON10 本選・ISUCON11 本選は初期化を 2 回呼ぶ。2 回目の初期化でも整合性が取れること。
- **出典**: 各回のマニュアル（上の表）、[ISUCON12 予選の講評](https://isucon.net/archives/56850281.html)。

## 7. ベンチの出力から読み取る

### ポータルの結果（成否・点・メッセージ・警告）を読む

- **効く条件**: 点が出ない、FAIL、点が不安定。メッセージの読み方が分からない。
- **やり方**:
  - 成否（PASS/FAIL）、点、メッセージの種類を見る。メッセージの末尾に `(critical error)` や `（タイムアウトしました）` が付く回がある（ISUCON9・10）。
  - メッセージは、同じ内容のものが 1 つにまとめられることがある。件数と表示の数は一致しない（ISUCON9 のマニュアル）。
  - ISUCON14 は、ワーニングと critical を別に扱う（200 件で打ち切り）。
  - ISUCON12 予選は、ベンチのログに「参加者が N 人増えました」「N 人の参加者が離脱しました」が出る。負荷の増減が読める。
- **確かめ方**: 走行ごとに、点・成否・人数・メッセージの上位を、表（`history`）に書く。コミットとの対応を取る。
- **出典**: [ISUCON9 予選のマニュアル](https://github.com/isucon/isucon9-qualify/blob/master/docs/manual.md)、[ISUCON14 のマニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)、[ISUCON12 予選のベンチのソース](https://github.com/isucon/isucon12-qualify/blob/main/bench/scenario.go)、`isucon-kit/tools/noise/README.md`

### 初期実装のベンチで、モデルを検算する

- **効く条件**: スコアの式を書いた後。どの項が支配的かが不確か。
- **やり方**:
  1. ベースライン（初期実装）の点と、人数・件数を、式に入れて、1 人あたりの点を出す。
  2. 理論上の上限と比べる。
  3. 順位表の上位の点（序盤の上位の伸び）と比べる。説明できない差を、問いにする。
- **確かめ方**: 検算が合うまで、改善の優先度を決めない。
- **危険**: 1 位の点が上限の見積もりを超える。前提のどれか（人数の上限・単位・数えていない操作）が違う。モデルは、順位表と突き合わせて直す。
- **出典**: `isucon-kit/docs/strategy.md`。

## よくある失敗

- **負荷が増えない原因を、台の処理量だと決める。** 負荷（人数）が上限に届いていた、または、ベンチ側の待ち（動線の条件）だった可能性がある。
- **減点がないから、エラーを許容してよいと読む。** FAIL と、加点されない操作が残る。
- **499 を見て慌てる。** 負荷テスト終了時の強制切断は、スコアにも検証にも影響しない（回による）。
- **initialize の時間を縮めることに時間を使う。** 負荷テストの時間は削られない。縮める価値は、制限の余裕と失敗しないこと。
- **initialize だけでキャッシュを作る。** 再起動後に空になる。
- **ベンチを見分けて 503 や固定の応答を返す。** 失格になりうる。マニュアルが明示した場合だけ。
- **手元のブラウザ・手動のアクセスの速さで、ベンチ中の挙動を決める。** ISUCON9 予選の配送 API は、ベンチ中だけ約 0.8 秒の遅延があった。
- **モデルを順位表と突き合わせない。** 1 位が上限を超えたら、前提が違う。
