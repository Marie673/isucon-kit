## A. 仕様の振る舞い（何を返せばスコアになるか）

序盤に、アプリの特性（`docs/design.md` の B）の最初の手順としてメインエージェントが埋める（skill `app-profile` の 0）。振る舞いの正は **マニュアルと API の仕様書**。初期実装ではない。

### A. なぜ要るか

振る舞いの正しさを初期実装で判断すると、マニュアルにあるボーナスを要件から落とし、ベンチの「got=400, want=200」を取り合いのせいだと思い込む。この表は数分でできて、仕様と初期実装の食い違いが見つかる。

### A1. スコアになる操作ごとの振る舞い

スコアになるエンドポイント（`docs/design.md` の C1 の配点の表）を、上から全部並べる。1 行に 1 つの操作。

| 操作（API） | 配点 | 成功の条件（何を返せば点か） | ボーナスの条件 | 減点・失格の条件 | 出典（マニュアル・仕様書の節） |
|---|---|---|---|---|---|
| | | | | | |

- **ボーナスの条件**は、取れるように作る要件としてボトルネック表に載せる（測るだけで終わらせない）。
- **失格の条件**（critical）は、テストにする。

### A2. 決まり（スコアを左右する判定）

成功・失敗を分ける判定を、1 つずつ書く。作り直すときは、ここを 1 か所に置き、仕様から書いたテストを付ける（`docs/tuning/16-rewrite-strategy.md`）。

| （例: 区間の検証。同じ駅・逆向き・止まらない駅は 400） | | | |

### A3. 仕様と初期実装の食い違い

初期実装を読んで、上の 2 つの表と違う所を並べる。**どちらを取るかを 1 件ずつ決める。** 仕様に書いていない所だけ、初期実装に倣う。

## B. アプリとリクエストの特性

序盤に、スコアのモデル（`docs/design.md` の C）と並べて埋める（skill `app-profile`）。先に仕様の振る舞い（`docs/design.md` の A）を書く。

ここで決めるのは「このアプリは、どんな形の負荷を、いつ受けるか」。平均の負荷ではなく、**利用者がいつ・何をきっかけに・一斉に動くか**を書く。よくあるアプリ（SNS・EC・予約など）の見た目に引きずられて、別の型の負荷を想定しない。

数字には出典（マニュアルの節、capture、job 番号）と印（【M】【B】【推】）を付ける。

### B5. 負荷を集中させる条件と、こちらで選べる値

速くしたのにスコアが伸びない、速くすると減点が増える、は**上限のしるし**。上限は、利用者・要求が一部に集中する条件から来ることが多い。

| 集中させる条件 | 例 | このアプリでは | 根拠 |
|---|---|---|---|
| 日付・季節・時間帯 | 連休・月末・受付開始 | | |
| 人気の対象 | 特定の列車・商品・人気の利用者 | | |
| 区分 | 地域・テナント | | |

**こちらで選べる値**（initialize の応答・設定・マニュアルが許す範囲で、ベンチの振る舞いを変えるもの）。選べる値は、そのまま施策になる。**需要の作り方**（利用者に何を見せるか: 空きの一覧、`retry_after_ms` のような次の要求までの間隔、キャッシュのヘッダ、接続を閉じるか）も選べる値に入れる。名前解決の答え（どのサーバーを返すか・TTL）を選べる問題では、それはサーバーの割り当てそのもので、構成の判断に入れる。供給が足りないときに需要だけ生むと、待ちが溜まってスコアにならず、相手（ベンチ）も重くする。

| 値 | 選べる範囲（出典） | 今の値 | 変えると何が起きるか（予想） | 試した結果 |
|---|---|---|---|---|
| （例: 予約可能な日数） | （例: 10〜366。マニュアルの節） | | | |

- マニュアル・仕様書で「〜を返す」「〜を設定できる」「〜の範囲で」を探す。initialize の応答の項目は全部ここに並べる。
- **許される範囲を確かめる。** 範囲はまずマニュアル・仕様書から読む。書かれていなければ、初期実装が返す値の近くで確かめる。範囲の外の値をわざと返してベンチの検査を探らない。
- 値を変える試しは 1 本ずつ。スコアの帳簿（`docs/design.md` の C5）の取りこぼしと減点が、どう動くかを見る。

## C. スコアのモデル

序盤に、メインエージェントが埋める（skill `score-model`）。

各節の数字には出典（マニュアルの節、ベンチの記録の job 番号）を付ける。マニュアルだけで書けたものに【M】、ベンチの記録が要ったものに【B】、推測に【推】を付ける。

### C1. スコアの式

```
点 = Σ（ 件数 × 配点 × 倍率 ） − 減点
```

| 項 | 中身 | 出典 |
|---|---|---|
| 件数を決めるもの | （例: 利用者の数 × 1 人あたりの操作の回数） | |
| 配点 | （API・操作ごとのスコアの表） | |

| 減点・失格 | （エラー・タイムアウト・整合性の違反） | |

### C2. スコアの増え方と支配的な項

合計のスコアの目標は書かない。どの項をどう動かせばスコアが増えるかを書く。

- 項ごとに: 何で決まるか、上限、今どれだけ取れているか（例: 利用者の増え方、1 人あたりのスコア）: 
- **一番大きい項**（ここがスコアの大半を決める）: 
- いまのスコアのうち、どの項がどれだけか（ベースラインのベンチから）【B】: 

| 項 | 点 | 割合 |
|---|---|---|
| 基本点（成功 × 配点） | | |
| ボーナス（マニュアルの加点の条件ごとに 1 行） | | |
| 減点（エラー・タイムアウト。理由ごとに 1 行） | | |

ボーナスと減点は、**差し引きの 1 つの数にまとめない**。別々に数える（まとめると、ボーナスが取れていないのか、減点が多いのかが見えない）。

### D7. 作り直す前に答える問い

構成の判断（制約の表と最初のベンチで出す）で「仕様から作り直す」を選ぶかどうかは、6 節の表で決め、ここの問いは判断の後も並行して答える。答えが判断の前提を崩したら出し直す（skill `main-loop` の「作り直すとき」）。答えは作り直しの設計にもそのまま入る。

- 全部を埋めるまで判断を待たない。形を決めるのに要る問いから答える。
- **初期実装は正としては使わず、計測の道具として使う。** 負荷をかけないと出ない答え（集中・取りこぼし・ボーナスの取れ方）は、初期実装のままベースラインと実験のベンチを流して取る。
