# ピークのキャパシティ

スコアのモデル（`docs/design.md` の C）と並べて、早いうちにやる。雛形は `docs/design.md` の D。

## なぜ要るか

ベンチの大半は CPU が空いていて、最後のピークの数十秒だけ全サーバーが張り付くことがある。平均の負荷で構成を決めると、一番大きいピークが 1 台に集まる。ピークの計算は構成を変えられるうちにする。

**キャパシティの計算は、スコアのモデルのどの項に効くかとセットで使う。** 足りない資源を見つけても、その項が頭打ちなら、スコアは伸びない。

## 手順

1. **サーバーを知る。** inventory の結果と `tools/cpu-features` の表を 1 節に貼る。サーバーによって速さが変わる処理（SHA・AES・SIMD）を必ず書く。サーバーの間の遅延・帯域も。
2. **1 回あたりのコストを測る。** ベースラインのプロファイル（perf・pprof・トレース）から、ピークで多い処理の 1 回の CPU・DB の時間・転送量を出す。
   - 手元が ARM なら、そのまま使わない。本番と同じ系統の CPU で microbench を取る（`tools/lab-aws`）。CPU の機能が違うと、効き目が逆に出ることがある。
   - 「仕様で減らせない処理」と「実装で減らせる処理」を分ける。
3. **ピークの処理量を出す。** design.md の C のピークの大きさ（同時の人数）× 1 人あたりの処理 × 1 回のコスト。最大のピーク（一番大きい区分の、最後の段階）で計算する。区分ごとにピークの時刻がずれるなら、それも書く（ずれていれば、空いているサーバーを借りられる）。
4. **突き合わせる。** サーバーごとに「ピークで必要な CPU 秒」と「使える CPU 秒（vCPU × ピークの幅）」を比べる。DB の接続の数も、ピークの同時数から逆算する。
5. **構成を決める。** 足りないサーバーがあれば、設定の調整では解けない。次のどれかを選び、案ごとに上の表で効果を計算する。
   - 配る: どのサーバーでやっても結果が同じ計算を、空いているサーバーに回す
   - 軽くする: 命令セット・まとめ計算（SIMD）・事前計算
   - 外す: ピークの間だけ後回し・絞る（配点が小さく重い処理）
   - 無くす: メモリに持つ。無効化は書き込み側から送る（読むたびに鮮度を DB に聞かない）
6. **却下した案と、却下が何に依存しているかを書く。** 15:00 に前提を見直す。
7. **制約の表と、0 から考え直す表を作る。** `docs/design.md` の D6。外のもの（ベンチのクライアント・決済などのサービス）の性質も制約に入れ、計測で根拠を付ける（nginx のログに `$server_protocol`・`$ssl_session_reused`・`$connection_requests` などを足す）。層ごとに最善と今の形を並べ、差をボトルネック表の候補にする。
8. **設計を変える問いに答える。** `docs/design.md` の D7 の問いのうち、形を決めるのに要るものから、出典つきで答える。全部を埋めるまで判断を待たない。足りない答えは、ベンチと実験（skill `probe-experiments`）で取りにいく。

## 出口

- 構成の判断は、理屈がつながったときにメインエージェントが自分で出す。「作り直す」も選択肢に入れ、「見たもの → 考え → 決めたこと」の 3 段で `docs/DECISIONS.md` に書く。
- 決まった構成の作業を、作戦ボード（`docs/README.md`）のボトルネック表の順番に落とす。

## 注意

- 平均の数字で決めない。ピークの数秒で決める。
- 「どこが遅いか」ではなく「どこで足りなくなるか」を計算する。遅い API の順と、足りなくなる資源の順は違う。
- 計算と実測が合わなければ、計算の前提（1 回のコスト・同時数）を測り直す。
