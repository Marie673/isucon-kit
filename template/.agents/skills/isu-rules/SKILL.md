# isu-rules — ルール考古学

桁の違う手は、点の仕組みの理解から出る。
チューニングより先に「何をすれば点が増えるか」を正確に知る。

## 原則

- **すべての主張に出典**（マニュアルの節名＋引用、コードの file:line、results の id）。出典がないものは「仮説:」と書く
- 調査資料に憶測を混ぜない。わからないことは「不明」と書き、確かめ方を添える
- 変更・実装はしない（考察のみのターン）

## 並列に分ける調査（subagent が使えるなら各1つ）

1. **スコア式**: 何が加点で何が減点か。重み。エラーの扱い（何件で失格か）。タイムアウトの扱い
2. **ベンチマーカーの挙動**: シナリオの流れ、負荷の上がり方（何をすると負荷が増えるか）、ポーリング間隔の指定（Retry-After 等）、どのレスポンスを検証しているか / していないか
3. **API 仕様と整合性**: 各エンドポイントのレスポンス要件、データ反映の遅延許容（何秒以内に反映されていればよいか）、キャッシュしてよい範囲
4. **initialize と再起動**: initialize が何をリセットするか、制限時間、追試で何を確認されるか
5. **初期実装の重い所**: ルーティング一覧と、各ハンドラのクエリ・ループ・外部呼び出し

## 出力（docs/RULES.md に追記してコミット）

- スコア式（式そのもの＋出典）
- 「仕様が許す余地」リスト: 遅延してよいもの、省略してよいもの、まとめてよいもの、ベンチが見ていないもの
- 整合性・禁止事項（壊すと失格 / 減点）
- initialize / 再起動の条件

## 形を考える材料

作り直すか、どんな形にするかを主ループが考えるための事実を書く。結論はここでは出さない。

- 全エンドポイントの入出力と副作用
- データの大きさと増え方（変わる部分と変わらない部分）
- 整合性の要件（反映の遅延の許容・トランザクションの境界）
