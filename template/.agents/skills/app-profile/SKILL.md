# アプリとリクエストの特性

序盤に、スコアのモデル（skill `score-model`）と並べてやる。雛形は `docs/design.md` の A と `docs/design.md` の B。

## なぜ要るか

負荷の型は、見た目の似たサービスからは分からない。

- 負荷は平均ではなく、特定のきっかけの直後の数秒に集まることがある。常時ばらけた負荷を思い浮かべて作ると、ピークに耐えられない。
- スコアが利用者の行動の連鎖で決まることがある。先に動いた人が見る状態しだいで、後のスコアが取れない。
- 利用者が増える条件は、特定の動線が時間内に終わるかで決まることがある。

アプリの型・動線・増える条件を最初に書けば、何を速くすべきかが早く決まる。

振る舞いの正しさを初期実装で判断すると、マニュアルにあるボーナスや、こちらで選べる値がスコアの上限を決めていることを見落とす。

## 手順

### 0. 仕様の振る舞いを書く（最初の 15〜20 分。subagent に渡してよい）
1. マニュアルの配点の表から、スコアになる操作を全部拾い、`docs/design.md` の A1 に「何を返せば点か・ボーナスの条件・減点の条件」を書く。**読むのはマニュアルと仕様書。初期実装ではない。**
2. 成功・失敗を分ける決まり（占有・運賃・検証など）を 2 節に書く。
3. 初期実装を読み、仕様と違う所を 3 節に並べる。どちらを取るかを 1 件ずつ決める。仕様に書いていない所だけ初期実装に倣う。
4. ボーナスの条件は、ボトルネック表の「順番」に要件として載せる。

### 1. マニュアルから型を決める（20 分）
1. マニュアルのアプリの説明・シナリオ・負荷ベンチの節を読み、`docs/design.md` の B1 を埋める。
2. **「似ている実在のサービス」と「負荷の型」を分けて書く。** 見た目が SNS でも、負荷は同期のピークかもしれない。
3. きっかけ（通知・時刻）が全員に同時に届くか、区分ごとにずれるか、最後の段階で重なるかを書く。

### 2. capture で動線を確かめる（30 分、ベースラインの後）
1. ベースラインのベンチを capture で記録する。無ければアクセスログで代わりにする。
2. 利用者（token・session）ごとに要求を時刻順に並べ、きっかけ（通知・期間の開始）からの相対時刻にする。
3. 典型の動線を 2 節の表にする。**直前の応答の何を見て次に進むか**を探す。ここにスコアの構造がある。
4. 最初に動いた人・最後に動いた人で、見える状態がどう違うかを書く。
5. 新しい利用者の動線（登録から最初の点まで）と、その所要時間を出す。

### 3. リクエストの特性（10 分）
- `tools/bench-window` でピークの窓と窓の外に分け、3 節の表を埋める。
- 熱いデータの大きさを見積もる（メモリに載るか）。
- 区分をまたぐ読みの割合は、思い込まずに測る。

### 4. 増える条件（ベンチの記録と並行）
- 区分 × 日の人数を、ベンチごとに並べ続ける。
- 増える条件・上限が分からなければ【推】で置き、skill `probe-experiments` で確かめる。

### 5. 集中させる条件と、選べる値（10 分）
- 利用者・要求が一部に集中する条件（日付・人気の対象・区分）を 5 節に書く。
- マニュアル・仕様書から、こちらで選べる値（initialize の応答の項目、範囲つきの設定）を全部拾う。選べる値は施策としてボトルネック表の候補に載せる。
- 「速くすると減点が増える」「スコアが伸びない」が出たら、ここに戻る。上限は集中から来ていることが多い。

## 出口

- スコアのモデル（`docs/design.md` の C）の 4 節「ベンチの利用者の行動」と 3 節「件数が増える条件」に、ここの結論を写す。
- ピークの大きさ（同時の人数・処理）を `docs/design.md` の D3 に渡す。
- 6 節の問いを `probe-experiments` に渡す。
- `docs/design.md` の A のボーナスの条件と、5 節の選べる値を、作戦ボード（`docs/README.md`）のボトルネック表の候補に載せる。
