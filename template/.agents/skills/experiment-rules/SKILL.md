# 実験の決まり

## なぜ要るか

同じ設定でもスコアは大きくぶれる。1 本の差で設定を切り替えると、入れては戻すを繰り返し、どれが効いたか分からなくなる。フラグも増え続ける。

## 1. ぶれの幅
- 序盤（ベースライン）に同じ commit で 3 回流し、`docs/experiments.md` の「ぶれの幅」に入れる。
- `tools/noise band --label baseline` で平均・範囲・変動係数を出す。
- 構成を大きく変えたら測り直す。

## 2. 比べ方
- `tools/noise compare <A> <B>` で判定する。結果は `差なし / 良い / 悪い / 本数不足`。
- **同じバージョンのスコアが 2 つの峰に分かれるときは、1 本の差で原因を決めない。** 3 本以上を流し、峰ごとにサーバーの使用率を並べる。計測の設定（slow log の全件記録・トレースの割合）が揺れの元のこともあるので、最終の計測の前に外して測る。
- **二峰は早く疑う。** 同じバージョンでスコアが 1 割以上離れた 2 本が出たら、その時点で同じバージョンを 3 回流し、峰ごとに区分（地域ごとの人数・段階ごとの成功）を並べる。峰が分かれている間は、スコアではなくプロファイル・サーバーの CPU 時間・区分ごとの成功率で採否を決める。
- **差なし・本数不足のまま、採否を決めない。** 採否が割れるなら、同じ設定と交互に 2 本ずつ流す。
- 点だけでなく、スコアのモデルの項（区分ごとの人数・段階ごとの成功）も並べる。スコアが同じでも、ある区分が伸びて別の区分が崩れていることがある。

## 3. 反映の単位
- 構成・設定の切り替え（フラグ・サーバーの割り当て・接続数・優先度）は、1 回の反映に 1 つ。
- コードの改善はまとめて反映してよいが、experiments.md の「変えたもの」に全部書く。

## 4. 窓で見る
- `tools/bench-window --anchor <ピークの時刻> --from -5s --to +30s` で、ピークの窓の秒単位のタイムラインとエンドポイント別の表を出す。
- ベンチ全体の平均（alp の合計など）は補助。ボトルネックの判断は窓で。
- トレースは採る割合を絞る（目安 10%）。100% だと、それだけで CPU を約 1 割使う。

## 5. フラグ
- 入れる前に `tools/flags new NAME` で `docs/flags.md` に行を足し、目的・根拠・消す条件を書く。
- 状態は `試験中 → 採用 / 廃止`。試験中のまま 2 時間を超えたら、`tools/flags lint` が知らせる。採るか消すかを決める。
- 廃止したフラグは、コード・設定・DB のトリガーなどの名残まで消す。
- 15:00 にすべての試験中のフラグを片付ける。

## 6. 最終ベンチ
- 最終スコアが最後に流した 1 本で決まる回は、本数を決めずに `tools/stop-rule` で止める。凍結のバージョンの点（fail は 0）の一覧と、締め切りまでに流せる本数から閾値を出し、直前の 1 本が閾値以上なら止め、下回ればもう 1 回流す。

## 7. 戻すとき
- 戻すのも 1 つの実験。戻した後の 1 本も experiments.md に書く。
- 失格・大きな低下（ぶれの幅の 2 倍以上）が出たら、疑わしい変更を 1 つずつ戻す。まとめて戻すと、次に同じ穴に落ちる。
