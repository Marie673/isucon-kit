# 12 静的ファイルと画像の配信

当日のマニュアルが優先する。**配布された静的ファイル（JavaScript・CSS・画像など）の内容を変えてはいけない**ことが多い。初期データの画像・履歴の期待値、画像 URL の署名と期限、削除した画像を返してよい猶予も、問題ごとに決まる。失格につながりやすいのは、静的ファイルの改変、初期データの画像の取りこぼし、削除・無効化した画像を返し続けること、永続化（再起動後に画像が残ること）を捨てること。

## この章で扱う範囲

- DB に入った画像をファイルへ書き出す方法（初期データの移行、initialize との整合、書き込み直後の読み）。
- nginx で画像を返す方法（直接配信、`X-Accel-Redirect`）。詳細な設定は 03 章。
- 304・Cache-Control を効かせる方法と、ベンチがキャッシュするかを確かめる方法。
- 画像の変換・リサイズの事前生成、JPEG の検査、画像 URL の署名のコスト。
- 帯域の見積もり、画像の削除・無効化の扱い、DB に画像を残す場合の最適化。

扱わないもの: nginx の設定の細部（03 章）、台の間の画像の複製と共有（11 章）、外向き帯域の制限と MTU（13 章）、アプリの画像ライブラリ。

## 最初に見るもの（当日の 5 分チェックリスト）

1. **画像・静的ファイルが全リクエストのどれだけか。** アクセスログを URI で集計する（01 章の計測、alp）。件数・合計の転送量（`$body_bytes_sent` の合計）・p50 の応答時間。
2. **画像はどこに保存されているか。** DB の BLOB（bytea）か、ファイルか、外部か。初期データの画像の枚数・合計の大きさ（`SELECT count(*), sum(octet_length(data)) FROM ...`、`du -sh`）。
3. **画像がアプリを通っているか。** アクセスログの `$upstream_response_time` があれば、アプリ（と DB）が画像を返している。
4. **ボトルネックはどこか。** アプリの CPU・DB の I/O・外向き帯域のどれか。外向き帯域が上限なら、CPU 側の手（直接配信、キャッシュ）は効かない（下の「帯域の見積もり」）。
5. **ベンチがキャッシュを使うか。** 同じ画像を何度も取りに来るか、`If-None-Match`・`If-Modified-Since` を送るか（アクセスログ・パケットで確かめる）。
6. **マニュアルの制約を読む。** 静的ファイルの改変の禁止、画像の変換・圧縮が許されるか、削除した画像の猶予、画像 URL の署名の仕様。
7. **画像の扱いの仕様を確かめる。** 書き込み直後に読まれるか、削除の後に取れなくなる必要があるか、権限（認可）が要るか、初期データの画像と履歴の期待値。

## 画像の置き場

### 画像がボトルネックかを見極める（アプリ・DB・帯域のどれか）

- **効く条件**: 画像の配信が点に効いていそうなとき（画像 GET が全リクエストの大半、または転送量が大きい）。
- **やり方**: 次の表で、ボトルネックを切り分けてから手を選ぶ。
  | 観測 | ボトルネック | 手 |
  | --- | --- | --- |
  | アプリの CPU が画像の読み出し・署名・変換で高い | アプリの CPU | ファイルへ出して nginx から返す（下）。署名・変換を軽くする |
  | DB の I/O・接続が画像の読み出しで埋まる | DB | 画像を DB から外す。DB に残すなら `data` 列を読まない（下の最適化の項） |
  | 台の外向き帯域が上限（`sar -n DEV`、`$body_bytes_sent` の合計 ÷ 時間 が回線の上限に近い）。CPU・DB には余力 | 帯域 | 転送量を減らす（304・キャッシュ・圧縮）。入口を増やす（11 章）。CPU の手は効かない |
  | 台をまたぐ画像の取得が遅い | 台の間の帯域・遅延 | 11 章、13 章 |
- **確かめ方**: CPU・DB・帯域のそれぞれを同じ負荷の窓で測る。画像だけを直したときの点の変化。
- **危険**: 帯域がボトルネックのとき、アプリを経由しない直接配信に替えても点は伸びなかった実例がある（動画。広告のリダイレクトを削っても帯域制約下では効果が出ない。ハッシュ URL の proxy_cache で外向き帯域は減らない）。
- **出典**: 実例: kazeburo（ISUCON4 本選、1Gbps の制約下）、eagletmt（ISUCON7 予選）、（画像帯域の選定手順）。

### DB の画像をファイルに書き出す（初期データの移行）

- **効く条件**: 画像が DB の BLOB（bytea）に入っていて、画像 GET が DB の I/O・アプリ・接続を使う。
- **やり方**: 移行の方式は 3 つ。画像の枚数と大きさで選ぶ。
  | 方式 | 内容 | 向く場面 | 注意 |
  | --- | --- | --- | --- |
  | 事前に作っておく（デプロイ時・競技の序盤に 1 回） | 初期データの画像は変わらないので、競技の序盤にファイルへ出し、各台に置く | 初期画像が多く、不変 | initialize でそのファイルを消さない。ファイルが欠けたとき DB へフォールバック |
  | 遅延して書き出す（初回アクセス時） | 読んだ画像をファイルに残す | 一部の画像しか読まれない | 初回は DB から。並行する書き込みで半端なファイルを公開しない |
  - 書き込みは**一時ファイルへ書いてから `rename`**（原子的に置く）。途中で失敗した不完全なファイルを公開しない。
  - 画像を全量メモリに読んでから書く処理は、ストリームコピーに替えられる。保存ファイル名のためだけの全量ハッシュ計算を省く実例もある（ただし衝突・上書き・参照 URL の要件を満たす別の決め方が要る）。
  - アップロード時にも、ファイルへ書く。画像のハッシュ（`ETag` や URL に使う値）は、保存時に計算して列に持つ（読むたびの再計算を省く）。
  - 配信は nginx の `try_files $uri @app;`（ファイルがあれば返し、無ければアプリが DB から返す）。認可が要る画像は `X-Accel-Redirect`（03 章）。
- **確かめ方**: 画像 GET のアクセスログで `$upstream_response_time` が出なくなる（nginx が直接返している）。ファイルの本文のハッシュが DB の本文と一致する（全件または抜き取り）。初期データの履歴・画像の取得が、初期データの期待値と一致する（critical の対象になりうる）。
- **危険**:
  - **初期データの画像を取りこぼす・内容が変わる**と、整合性チェック（初期データの履歴・画像の取得）に落ちる。
  - **永続化**: ファイルを置く場所は再起動後も残る（tmpfs・`/tmp` に置かない。02 章）。ベンチ中にアップロードした画像が再起動後に取れること。
  - **アップロード直後の読み**: アップロードの応答の直後に GET が来る。ファイルを書き終えてから応答する。ファイルがまだ無いときのフォールバック（DB 保存・アプリ）を用意する。
  - アップロードされた不正な画像の扱い（検査して 400 を返す、など）を変えない。
  - 複数台: 台をまたぐ複製・共有は 11 章（複製の遅れ、更新時刻の不一致）。
  - 実例: makino（ISUCON11 予選。isu.image のバイナリをファイル保存。「アップロード直後の参照、権限、初期化、複数台での保存先を確認する」）、ISUCON13。ハッシュを列に保存
  - [kujira16 ISUCON11 予選](https://kujira16.hateblo.jp/entry/2021/08/22/231020)（画像を nginx から配信）
  - [sorah ISUCON13](https://diary.sorah.jp/2023/11/28/isucon13)（アイコンをファイルに書き出して nginx から静的ファイルとして返し、スコアが 12,768 から 20,160 に上がった）

### initialize との整合

- **効く条件**: 画像をファイル・メモリ・別の台に持つようにした。
- **やり方**: initialize で、**ベンチ中に追加された画像を消し、初期データの状態に戻す**。
  - 初期データの画像は変わらないので、ファイルを消さずに残す。ベンチ中に追加された側だけを消す。
  - 独自に足したキャッシュ・複製先（ほかの台のファイル、メモリのキャッシュ）も初期化する。
  - initialize の秒数（60 秒など、マニュアルの制限）に収める。初期化が長くても、負荷テストの時間は削られないことが多いが、制限を超えると失格になりうる。
- **確かめ方**: ベンチを 2 回続けて流す（2 回目が 1 回目の画像に影響されない）。initialize の秒数。initialize の後、初期データの画像と、ベンチ中に追加した画像が、期待どおりの状態か。
- **危険**: **全台・全キャッシュ・複製先の初期化の取りこぼしは、整合性チェックの失敗になる**（11 章の「初期化を全台に伝える」）。初期化で画像のメタデータ（ハッシュ・URL）の寿命を変えたとき、2 回目のベンチで失敗した実例がある（決済先 URL を保存して再利用した実例も同じ型。値の寿命をベンチ 1 回に合わせる）。
- **出典**: 初期化の確認。

### 書き込み直後の読みと、画像の書き込み順序

- **効く条件**: 画像のアップロード（投稿・プロフィール画像の変更）のすぐ後に、その画像の GET が来る。
- **やり方**: **実体を先に保存し、見える参照（DB の行・URL）を後に作る。** 応答を返す時点で、画像が読めること。ファイルと DB を両方持つなら、ファイルを書いた後に DB の行を commit する。ファイルがまだ無いときは、DB かアプリへフォールバックする。
  - 画像変換を非同期にする（キューとワーカー）と、アップロード直後の GET に間に合わない。直後の GET の要件を確かめてから非同期にする（ISUCON3 本選で非同期変換を試し、設計がまずかったと振り返った）。
- **確かめ方**: アップロードの応答の直後に GET して、200 が返る。複数台では、別の台の nginx から GET する。
- **危険**: 参照が先に見えると、画像が 404 になる。画像と参照の更新を原子的にする（画像の更新とハッシュの更新）。
- **出典**: （「書き込みの順序（実体が先、可視な参照が後）」）。

## 配信とキャッシュ

### 304・Cache-Control を効かせる（ベンチがキャッシュするか）

- **効く条件**: 同じ画像・静的ファイルを何度も返していて、帯域か CPU がボトルネック。アクセスログで、同じ URI が繰り返される。
- **やり方**: nginx から返すファイルには、`expires`・`Cache-Control`・`ETag`・`Last-Modified`（03 章）。アプリが返す画像には、アプリが `ETag`・`Last-Modified`・`Cache-Control` を付け、`If-None-Match` で 304 を返す。画像の URL にハッシュが入っていて、内容が変わらないなら、長い `max-age` にできる。
  - **ベンチがキャッシュ・条件付き GET を使うかは、問題による。** ヘッダを付けても、条件付き要求が来ないことがある（ETag・Last-Modified だけでは来ず、Cache-Control も返すと 304 が使われた実例）。`expires` だけでは増点せず、`public` を足すと得点が約倍になった実例もある（ベンチが共有キャッシュのように振る舞うという説明は筆者の推定）。
  - 要求にそもそも条件付きヘッダが無いか、パケットキャプチャで確かめる（ISUCON7 予選の実例は、パケットで `If-Modified-Since`・`If-None-Match` が見当たらないことに気づいた）。
- **確かめ方**: アクセスログに `$http_if_none_match`・`$http_if_modified_since`・`$status`（304）を出す（条件付き GET と圧縮のヘッダを専用ログに出した実例）。同じ画像の再送回数、304 の割合、外向きの bytes。
- **危険**: **認証・Cookie・利用者依存の応答を `public` にしない。** 更新の反映を即時に求められる仕様（権限の変更、削除した画像が 5 秒以内に取れなくなる）に長い TTL を使わない。ヘッダだけでクライアントが必ず条件付き要求を送るとは扱わない。ヘッダを付けても、304 が返っても、別の画像の転送が支配的なら効かない。
- **出典**: [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)（`public`・`private`・`max-age`、共有キャッシュ、ヒューリスティックな鮮度）、[RFC 9110 条件付き要求](https://www.rfc-editor.org/rfc/rfc9110.html#name-conditional-requests)、[nginx headers module](https://nginx.org/en/docs/http/ngx_http_headers_module.html)、[joker1007 ISUCON7 予選](https://joker1007.hatenablog.com/entry/2017/10/23/100000)（`public` で約倍。304 を最後まで返せなかった）。

### 画像を複数台で返すときの 304（更新時刻・ETag をそろえる）

- **効く条件**: 画像を複数台の nginx から返している。台によって `Last-Modified`・`ETag` が違うと、台をまたいだ条件付き GET が 304 にならず、全体を送り直す。
- **やり方**: 同じ URI を各台から取得し、本文のハッシュ、`ETag`、`Last-Modified`、`Cache-Control` を比べる。複製のとき、更新時刻を元に揃える（WebDAV の PUT は `Date` ヘッダで更新時刻を指定できる）。秒境界の前後・複製中の台の切替も試す。
- **確かめ方**: 同じ URI で各台に `curl -sI`。条件付き GET が全台で 304。
- **危険**: 実例（ISUCON7 予選）は、初期画像を各台に置いたときに更新時刻を揃え忘れたことが主因と筆者が事後に推定したが、確定した原因ではない（個別に確認した画像は ETag が一致していた）。mtime を揃えるだけで全部直ると決めつけない。
- **出典**: 実例: joker1007（ISUCON7 予選）、[nginx dav module（PUT の Date）](https://nginx.org/en/docs/http/ngx_http_dav_module.html)。

### 認可つきの画像（署名付き URL）と X-Accel-Redirect

- **効く条件**: 画像に認可・署名の検査が要り、検査後の本体の転送だけを nginx に任せたい。
- **やり方**: アプリが署名・権限を検査し、本体は返さず `X-Accel-Redirect` で内部の位置を指す（03 章）。内部の位置は `internal;` にして、外から直接叩けないようにする。ファイルが無いときのフォールバック（再度の認可つきでアプリが返す）を用意する。
- **確かめ方**: 署名が不正・期限切れ・無効化された画像が 403 を返す。内部のパスを外から直接叩いて 404 になる。
- **危険**: 署名の形式・期限・検証の結果は変えない（仕様）。認可を nginx 側で省かない。実例では、アプリで ETag の判定だけをして画像は nginx から返す構成が、304 は返せても puma の CPU が残った（proxy_cache にすればよかった、と筆者は振り返った）。
- **出典**: 実例: kujira16（ISUCON11 予選）、sorah（ISUCON13 本番。[ブログ](https://diary.sorah.jp/2023/11/28/isucon13)）、（`/_isu_images/` に `internal;`）、[nginx proxy module（X-Accel-Redirect）](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。

## 画像の処理のコスト

### 画像の変換・リサイズの事前生成

- **効く条件**: 画像のリサイズ・切り抜き・形式変換を、要求のたびにしている。外部コマンド（`convert`・`identify`）を起動している。
- **やり方**: 取得要求の多いサイズを、事前に（初期画像は初期化の前に）生成しておく。外部コマンドの起動（fork）は、アプリのプロセスのライブラリに替える。事前生成の対象が多すぎるなら、実測で絞る（直近・頻出サイズ・新着だけ）。
- **確かめ方**: 画像 GET の応答時間と CPU。出力のサイズ・切り抜きの位置が元と同じか比べる。
- **危険**: **画像の変換が許される大会に限る。配布された静的ファイルの改変にならないか確かめる**（出力が変われば互換検査に落ちる。crop と resize の順序を逆にして最終 fail の原因の候補になった実例）。事前生成は、初期化から再生成できること。全件の事前変換でメモリ（Redis）が溢れた実例がある。置換だけで速くならない実例がある（外部コマンドをライブラリ化しても横ばい）。非同期にすると直後の GET に間に合わない。
- **出典**: 実例: tagomoris（ISUCON3 本選）。

### JPEG の検査・デコードを必要な分だけにする

- **効く条件**: アップロードされた画像を、検査のために全画素デコードしていて、その CPU が山の瞬間（一斉の投稿）に飽和する。
- **やり方**: 仕様が要求する検査（不正な画像の検出）を保ったまま、デコードの量を減らす。
  - 冒頭で明らかに不正（JPEG の SOI `FF D8` が無い）なら、全体を読む前に 400 を返す。
  - 速いデコーダ（SIMD）、検査の結果を覚える。
- **確かめ方**: 1 枚あたりの CPU（microbench。本番と同じ系統の CPU で）。山の瞬間の CPU 秒（同時の枚数 × 1 枚のコスト）。
- **危険**: 検査を弱めて、不正な画像を通すと、critical（不正な画像の 400）になりうる。サイズだけの拒否や nginx の 413 化は、仕様のエラーの形（400 か 413 か）を変える。

### 画像 URL の署名（HMAC などを毎回計算している）

- **効く条件**: 画像 URL に署名（ハッシュを連鎖して計算するもの）が付き、画像 GET・投稿のたびに検証・生成している。`perf` でハッシュ関数が上位。SHA 専用命令が無い台がある（11 章の cpu-features）。
- **やり方**: 一意な署名は覚える（期限を丸めて同じ署名を使い回す。仕様が許す範囲で）。複数の署名をまとめて計算する（SIMD のマルチバッファ）。計算をまとめて、命令のある台へ回す。
- **確かめ方**: 署名の CPU 割合（perf・pprof）。台ごとの違い。
- **危険**: **署名のアルゴリズム・URL の形式・検証の結果は変えない（仕様）。** 期限の丸めは、仕様の許す範囲でメインエージェントが根拠を記録して決める。手元が ARM（SHA 命令あり）だと、本番の x86 と効き目が逆に出る。
- **出典**: `tools/cpu-features/README.md`。

## 帯域

### 帯域の見積もり

- **効く条件**: 外向き帯域・台の間の帯域が上限に近いかを確かめたいとき。画像の転送量が大きい。
- **やり方**: 次の式で、台ごとの必要な帯域を見積もる。
  - 帯域（MB/s）＝ 同時の画像の数 × 1 枚の大きさ ÷ 許容の時間。
  - 100Mbps ≒ 12.5MB/s、1Gbps ≒ 125MB/s（単位の換算）。実効の値は測って決める。
  - 往復遅延が大きい経路では、1 接続の速度が BDP（帯域 × 遅延）で決まる。100Mbps・100ms の BDP は約 1.25MB（ソケットバッファの上限と `tcp_slow_start_after_idle` は 02 章）。
  - 台の間の実効帯域は `curl` で大きなファイルを取って測る（`iperf3` は台の間に入れてよいか確かめる）。
  - 実際の転送量は、アクセスログの `$body_bytes_sent` を時間で割る（走行の山の数十秒で見る。平均では山が見えない）。
- **確かめ方**: `sar -n DEV 1`（NIC の送受信）、`ss -ti`（`cwnd`、`delivery_rate`）。計算と実測が合うか。
- **危険**: 外向き帯域が上限に達していると、CPU・DB 側の手（直接配信、キャッシュ）は効かない。**帯域・遅延の制限を変更・回避してはいけない**。
- **出典**: 帯域がボトルネックで約 10 万点付近で止まった。

### 画像を圧縮・再圧縮しない（JPEG は圧縮済み）

- **効く条件**: 画像の転送量を減らしたくなるとき。
- **確かめ方**: 圧縮の前後の `$body_bytes_sent`、`$gzip_ratio`。
- **危険**: **画像の再圧縮・メタデータの除去は、画像の内容を変える。** 初期データ・Memories・エクスポートの期待値と一致しなくなる。PNG をさらに圧縮しても、サイズは減らなかった実例がある。
- **出典**: [nginx gzip module](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)。

### 複数の入口で帯域を分ける

- **効く条件**: 1 台の外向き帯域が上限で、台の CPU・DB に余力がある。
- **やり方**: 複数の台を、ベンチの対象（入口）にして、画像を各台から返す。全入口で同じデータ・認証を扱えること。
- **確かめ方**: 台ごとの外向き帯域。
- **危険**: 複数のターゲットが許されるか、マニュアルで確かめる。画像を全台に複製する必要がある（11 章。更新時刻・ETag をそろえる）。
- **出典**: 実例: ISUCON7 予選、ISUCON4 本選。

## DB に画像を残す場合

### DB の画像を読むコストを下げる

- **効く条件**: 画像を DB に残す（初期データが多い、複製の仕様上 DB が正）。画像 GET の応答が遅い、DB の I/O が高い。DB の複製（レプリケーション）の WAL に画像が載って帯域を使う。
- **やり方**:
  - `SELECT *` を避け、一覧・検索では画像の `data` 列を読まない。画像だけ別テーブルにする（画像を除いた列で検索できるようにする）。
  - PostgreSQL の bytea は、既定（EXTENDED）では圧縮を試す。JPEG のように圧縮されないデータでは、`STORAGE EXTERNAL`（圧縮を試さない）にすると、CPU が減る。
  - `wal_compression` は、フルページの書き込み（FPI）にだけ効く。JPEG の本体の WAL は圧縮されない。
  - 画像を DB の外（ファイル）に出すと、複製の WAL から画像が外れる。同期レプリケーションの待ちが画像の大きさで長くなるときに効く。
- **確かめ方**: 画像 GET の SQL の時間（`pg_stat_statements`）、WAL の量（`pg_current_wal_lsn` の差）、CPU。
- **危険**: 画像を DB の外に出す変更は、永続化・初期化・複製の整合に触る（上の項と 11 章）。`wal_compression` や `full_page_writes = off` は、永続性・回復に関わる設定で、`full_page_writes = off` は回復できない破損を起こしうる（PostgreSQL 公式）。画像の WAL を減らすために、永続化を弱める手を使わない。
- **出典**: [PostgreSQL: WAL の設定（wal_compression、full_page_writes）](https://www.postgresql.org/docs/16/runtime-config-wal.html)、[PostgreSQL: wal_compression](https://www.postgresql.org/docs/16/runtime-config-wal.html#GUC-WAL-COMPRESSION)。

## 削除・無効化

### 画像の削除・無効化を仕様どおりに扱う

- **効く条件**: 投稿・画像の削除、退会、プロフィール画像の変更・削除などの後に、その画像を取得できなくなる必要がある。画像をファイル・nginx のキャッシュ・複製・ブラウザのキャッシュなど、複数の場所に持っている。
- **やり方**: 仕様の猶予を確かめる。猶予の対象外（退会・プロフィール画像の変更/削除・置き換え）は、同期で無効化する。
  - 無効化は、DB の状態・ファイル・全台の複製・メモリのキャッシュ・`proxy_cache` の全部に伝える。署名が不正・期限切れ・画像が無効なら 403（仕様）。
  - 認可を `X-Accel-Redirect` の前（アプリ）で行うなら、削除の判定はアプリの状態で済み、ファイル自体は後から消せる、という設計が考えられる。
  - nginx の `open_file_cache`・`proxy_cache`・`Cache-Control` の TTL が、無効化の猶予より長くないか確かめる。
- **確かめ方**: 削除の応答の後、猶予を過ぎたら 403・404 になる。全台・全経路で。ブラウザ相当のキャッシュは、仕様の猶予内か。
- **危険**: **削除した画像を返し続けると、critical になる。** 長い TTL・複製・キャッシュが、無効化を邪魔する。
- **出典**: （内容が変わったのに古い検証値へ 304 を返さない）、[nginx core（open_file_cache）](https://nginx.org/en/docs/http/ngx_http_core_module.html)。

## 保存先の構造

### ファイル数が多いときのディレクトリ構造

- **効く条件**: 画像を数万〜数百万のファイルにする。1 つのディレクトリに大量のファイルを置く。
- **やり方**: ID やハッシュの先頭でディレクトリを分ける（`ab/cd/abcdef....jpg`）。nginx の `proxy_cache_path levels=1:2` も同じ考え方。ファイル数・inode の残り（`df -i`）を見積もる。
- **確かめ方**: `df -i`、`ls` の遅さ、ファイル作成の時間。
- **危険**: 初期画像が非常に多いと、書き出しに時間がかかる。initialize で全件を書き出さない（上の項）。
- **出典**: [nginx proxy module（proxy_cache_path の levels）](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)（ディレクトリの階層の考え方）。ファイルシステムのファイル数の上限は出典未確認（`df -i` で確かめる）。

## よくある失敗

1. **静的配信に移したら画面が崩れた。** MIME・パス・相対 URL・圧縮ヘッダ・`add_header` の継承。
2. **ヘッダを付けたが、ベンチが条件付き GET をしない・キャッシュしない。** 付けただけで効くと決めつけず、アクセスログとパケットで確かめる。
3. **帯域がボトルネックなのに、CPU 側の手を打つ。** 直接配信・proxy_cache・リダイレクト削減は、外向き帯域が上限だと効かない。
4. **複製した画像の更新時刻・ETag が台で違い、304 にならない。** 台をまたいで比べる。
5. **アップロード直後の GET に間に合わない。** 非同期変換・ファイルの書き込み順序。
6. **初期データの画像を取りこぼす・内容を変える。** 整合性チェックに落ちる。再圧縮・メタデータの除去・変換は、内容の改変になる。
7. **削除・無効化した画像を返し続ける。** キャッシュ・複製・ファイルの TTL（critical）。
8. **initialize で画像のファイル・キャッシュ・複製先を初期化し忘れる。** 2 回目のベンチで失敗する。
9. **画像を tmpfs・`/tmp` に置く。** 再起動で消えて、永続化の検査に落ちる（02 章）。
10. **画像の変換を置換だけで速くしようとする。** 外部コマンドをライブラリに替えても横ばいの実例がある。
11. **署名のアルゴリズム・URL の形式を変える。** 仕様違反（署名の高速化は、計算のまとめ・事前計算で）。
