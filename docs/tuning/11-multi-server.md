# 11 複数台の構成

当日のマニュアルが優先する。使える台の数・スペック・台の間の通信の決まり（ルーターを通すこと、遅延や帯域の制限を回避してはいけないこと、台のスペックを変えてはいけないこと）は問題ごとに違う。失格につながりやすいのは、永続化を捨てた複製、ルーターの迂回、外部への処理の委譲、初期化（全台・全キャッシュ）の取りこぼし。

## この章で扱う範囲

- 役割の分け方: nginx・アプリ・DB をどの台に置くか。
- DB を別の台に移す手順（待ち受けアドレス・権限・接続数）と、読み取りのレプリカ。
- パスや機能、利用者での振り分け。
- セッション・キャッシュ・画像を台をまたいで共有する方法（共有しない設計を含む）。
- 台の間の通信（プライベート IP、keepalive、遅延の見積もり）、初期化と再起動試験。

扱わないもの: nginx の設定の細部（03 章）、OS の設定（02 章）、DB のチューニング、画像の保存形式（12 章）、HTTP クライアント（13 章）。

## 最初に見るもの（当日の 5 分チェックリスト）

1. **台とスペックを表にする。** 台の数、vCPU、メモリ、プライベート IP、CPU のモデル。`bin/isu-inventory` の結果、`lscpu`、`/proc/cpuinfo`。CPU の機能は `tools/cpu-features`（下の項）。
2. **台の間の遅延と帯域を測る。** `ping -c 10`（往復）、同じリージョンか別か。遅延が 1ms 未満なら、台の間の往復は気にしなくてよい。数十 ms 以上なら、往復の回数がそのまま応答時間になる。
3. **ベンチ中の CPU・メモリ・ネットワークを台ごとに見る。** どの台が飽和していて、どの台が空いているか。平均ではなく、負荷の山の数十秒を見る（ベンチの窓。01 章の計測、`tools/bench-window`）。
4. **今、各台で何が動いているか。** `systemctl list-units --type=service --state=running`。初期の構成では、全台でアプリと DB が同じように動いていることが多い。使っていないものは止める（02 章）。
5. **ベンチがどの台にリクエストを送るか、どの台が得点に関わるか。** マニュアルで確かめる（ポータルが 1 台を叩くのか、全台か、ルーター経由か）。
6. **ボトルネックを確かめる。** DB がボトルネックならアプリを増やしても効かない。アプリの CPU がボトルネックなら DB を分けるより、アプリを増やす。

台を増やす前に、1 台での改善（インデックス、N+1、キャッシュ）を済ませるのが定石。全体の手順は isucon-kit の `docs/strategy.md`、台の配置の計算は `template/.agents/skills/capacity-plan`。

## 役割の分け方

### 配置は「どこで足りなくなるか」の計算から決める

- **効く条件**: 台が 2 台以上あり、どの台に何を置くか決めかねるとき。「遅い API の順」と「足りなくなる資源の順」は違う。
- **やり方**: capacity-plan の手順で、負荷の山の処理量（同時の人数 × 1 人あたりの処理 × 1 回のコスト）と、台ごとの使える CPU 秒（vCPU × 山の幅）を突き合わせる。足りない台があれば、設定の調整ではなく構成を変える。
  1. 台を知る（CPU のモデル・機能、台の間の遅延と帯域）。
  2. 1 回あたりのコスト（CPU・DB の時間・転送量）を、プロファイルやトレースから出す。
  3. 山の処理量を出す（平均ではなく、最大の山）。
  4. 台ごとに必要な CPU 秒と使える CPU 秒を比べる。DB の接続数も山の同時数から逆算する。
  5. 足りない台には、「配る」（どの台でやっても結果が同じ計算を空いた台へ）「軽くする」（まとめ計算・事前計算）「外す」（山の間だけ後回し）「無くす」（メモリに持つ）のどれかを選ぶ。
- **確かめ方**: 計算と実測が合うか。合わなければ、計算の前提（1 回のコスト・同時数）を測り直す。
- **出典**: isucon-kit `template/.agents/skills/capacity-plan/SKILL.md`、`docs/strategy.md`。

### 典型的な配置のパターン

- **効く条件**: 台が 2〜3 台のとき（ISUCON の標準は 3 台）。
- **やり方**: 代表的な型を表にした。台の役割とボトルネックで選ぶ。表の型 A〜E は、下の出典の構成を整理者（この章の筆者）が分類したもので、型の名前そのものには出典が無い（出典未確認の分類）。
  | 型 | 台 1 | 台 2 | 台 3 | 向く場面 |
  | --- | --- | --- | --- | --- |
  | A 標準 | nginx + アプリ | DB | アプリ（nginx の upstream に 2 台） | アプリの CPU がボトルネック。DB に余力がある |
  | B DB 分離だけ | nginx + アプリ | DB | （空き・Redis など） | DB が CPU・メモリを食って同居のアプリを圧迫している |
  | C 得点対象を分ける | 得点に効く Web 処理（vCPU の多い台） | DB と得点対象外の処理 | 入口・静的配信・キャッシュ | 台のスペックが違い、API の配点が偏る |
  | D 1 台に集約 | 全部 | 空き | 空き | 全部メモリに載せ、ネットワークの往復を無くす |
  | E 地域ごとの台 | 各地域の入口 + アプリ | 主 DB | 各地域の台に読み取りのレプリカ | 台の間の遅延が大きい |
  - 「典型: isu1 = nginx + app、isu2 = DB、isu3 = app」は定石集の記述。構成を決める前に、どれが CPU を食っているか確かめる。
  - 「インメモリへ全書き換えした後は 1 台集約が上位の定石」（ネットワークの往復が消える）も定石集の記述。ただし**永続化**が要る（再起動後にデータが残ること）。
  - 作問者の模範解答（ISUCON10 本選）は、1 台目（1GB・2vCPU）に Varnish・nginx の静的配信を、2 台目（2GB・2vCPU）にスコアに寄与しない Web 処理と MySQL・Redis を、3 台目（1GB・4vCPU）にスコアに寄与する Web 処理を置いた（C 型）。
- **確かめ方**: 台ごとの CPU・メモリ・ネットワーク、ベンチの点。構成を変える前後で、同じ commit で 3 本流して、ぶれの幅（`tools/noise`）と比べる。
- **危険**: 構成を変えたら、設定（接続先・台のリスト）と起動するサービスを台ごとに更新し、再起動試験で確かめる。使わなくなったサービスは `systemctl disable` まで。
- **出典**: [sorah ISUCON10 本選の解答](https://isucon.net/archives/55140539.html)、実例: 得点対象 API と対象外 API を異なる CPU 構成へ配置。

### 台ごとの CPU・命令セットの違い（cpu-features）

- **効く条件**: 台の CPU のモデルが違う（世代・ベンダー・クラウドのインスタンスタイプ）。同じコードが台によって速さが変わる。署名・ハッシュ・暗号・圧縮・JPEG・JSON などが CPU を食う。
- **やり方**: 各台の `/proc/cpuinfo`（`lscpu` でもよい）を取り、`tools/cpu-features` に渡して表にする。サーバーには接続しない道具で、取得は別の手順。
  ```sh
  ssh host1 cat /proc/cpuinfo > host1.cpuinfo
  ssh host2 cat /proc/cpuinfo > host2.cpuinfo
  tools/cpu-features/cpu-features host1=host1.cpuinfo host2=host2.cpuinfo
  ```
  先頭の警告が最優先（台によって速さが変わる処理）。SHA 専用命令（`sha_ni`）が無い台では、SHA-256 のソフト実装が数倍遅い。対策として、複数の署名をまとめて計算する（AVX2・AVX-512 のマルチバッファ）、結果を事前計算する、その処理を命令のある台へ回す、がある。
- **確かめ方**: 表の警告。実際の速さは microbench で測る（本番と同じ系統の CPU で。手元が ARM なら、そのまま当てはめない）。
- **危険**: 手元の Apple Silicon は SHA 命令を持ち、本番の x86 と効き目が逆になりうる。手元で測った SHA や SIMD の結果は、そのまま本番に当てはめない（isucon-kit の `tools/cpu-features/README.md`）。

## DB を別の台に移す

### 手順（待ち受けアドレス・権限・接続先・旧サービスの停止）

- **効く条件**: DB が CPU・メモリ・ディスク I/O を食って、同居のアプリ（nginx・アプリ）と奪い合う。台が複数あり、DB 専用の台を作れる。
- **やり方**:
  1. **DB を待ち受けさせる。** PostgreSQL は `listen_addresses`（既定は `localhost`。`*` で全インターフェース、プライベート IP を指定してもよい。再起動が要る）。MySQL は `bind_address`（既定は `*`。特定の IP を指定すると、その IP からだけ受ける。再起動が要る）。
  2. **アクセスを許可する。**
     - PostgreSQL: `pg_hba.conf` に `host <db> <user> <アプリ台のサブネット/マスク> scram-sha-256`（上から順に最初に一致したものが使われる。`pg_reload_conf` で反映）。
     - MySQL: アカウントは `'user'@'host'`。`CREATE USER 'app'@'192.168.0.0/255.255.255.0'` のように、IPv4 のネットマスクで書ける（8.0.23 以降は CIDR も）。`%` の使用は 8.0.35 以降で非推奨。アプリの接続元のアドレスが一致するか確かめる。
  3. **アプリの接続先を変える。** 環境変数・設定ファイルの DB のホストをプライベート IP に。`localhost`・Unix ソケットで繋いでいたものは、TCP に変える（DB のポートも）。ドライバの TLS・認証の方式も確認。
  4. **データを移す。** 同じ構成でダンプ・リストア、またはファイルのコピー（DB を止めて）。初期化（initialize）が DB のスキーマ・データを作り直す仕組みなら、新しい台の DB に対して動くか確かめる。
  5. **旧 DB を止める。** 旧台のアプリ・定期ジョブ・DB も `disable` まで止める。
  6. **ファイアウォール・セキュリティグループ**でポートが開いているか確かめる。
- **確かめ方**:
  - アプリの台から `nc -vz <DB の IP> 5432`（または 3306）。DB の台から `ss -ltn` で待ち受けのアドレス。
  - ベンチを 1 回流して通ること。**再起動して、全台が手作業なしで起動し、アプリが DB に繋がること。**
- **危険**:
  - **旧台に残った初期アプリ・定期ジョブが動き続けて、二重実行になった実例がある**（配車ジョブが DB 専用の台でも動き、二重配車が出た）。役割を変えた台のサービスは止める。再起動で復活しないか確かめる。
  - ポートが開いていても、台の間で切断される（tcpwrapper の `hosts.allow`、ファイアウォール）実例がある。
  - MTU が台の間で合わず、DB の認証で `Bad handshake` が出た実例がある（13 章）。
  - `bind_address`・`listen_addresses` を `*` にして、DB を外のネットワークに公開しない。許可は台の間のサブネットだけにする。
  - 起動順: アプリが DB より先に起動して 500 になる実例がある。アプリに接続のリトライを入れる。
  - 永続化を落とさない（`fsync` や `synchronous_commit` を切ると、再起動・クラッシュでデータを失う。下の項）。
  - [PostgreSQL: 接続設定（listen_addresses、max_connections）](https://www.postgresql.org/docs/16/runtime-config-connection.html)、[pg_hba.conf](https://www.postgresql.org/docs/16/auth-pg-hba-conf.html)
  - [MySQL: bind_address](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html)、[アカウント名](https://dev.mysql.com/doc/refman/8.0/en/account-names.html)
  - 、PowerDNS とその DB を別の台へ、Redis を別の台へ

### DB の接続数（アプリの台数 × プール）

- **効く条件**: アプリを複数台に増やした、または worker・プールを増やした後に `Too many connections`、接続の取得待ち、DB の CPU の増加。
- **やり方**: 「アプリの台数 × 1 台のプロセス数 × プールの大きさ」が DB の上限を超えないようにする。
  - PostgreSQL: `max_connections`（既定は通常 100。`superuser_reserved_connections` の分を引く）。**スタンバイの `max_connections` は、プライマリと同じかそれ以上でなければならない**（足りないと、スタンバイの読み取りが許されない）。
  - MySQL: `max_connections`（8.0 の既定は 151。出典の頁には書かれていないので、使う版の既定は `SHOW VARIABLES` で確かめる）。接続 1 本ごとにスレッドのバッファが要るので、最悪のメモリは接続数に比例する。FD も食うので `open_files_limit`・`LimitNOFILE` も合わせる（02 章）。
  - 山の同時数から逆算する（capacity-plan の手順 4）。
  ```sql
  -- MySQL
  SET PERSIST max_connections = 500;        -- 再起動後も残る
  SHOW STATUS LIKE 'Max_used_connections';  -- 実際の最大
  ```
- **確かめ方**: `SHOW STATUS LIKE 'Max_used_connections'`（MySQL）、`SELECT count(*) FROM pg_stat_activity`（PostgreSQL）、アプリのプールの待ち時間。
- **危険**: 接続を増やしすぎると DB が遅くなる（アプリの同時実行数を絞って安定した実例もある）。アプリのプールの大きさと、DB の `max_connections` を別々に調整して、合計を見ない失敗が多い。
- **出典**: [PostgreSQL 接続設定](https://www.postgresql.org/docs/16/runtime-config-connection.html)、[PostgreSQL hot standby（standby の設定は primary 以上）](https://www.postgresql.org/docs/16/hot-standby.html)、[MySQL: Too many connections](https://dev.mysql.com/doc/refman/8.0/en/too-many-connections.html)。worker を増やすときは、接続プールの合計を計算する。

### DB がボトルネックのとき、アプリの台を増やしても効かない

- **効く条件**: アプリを 2〜3 台に増やしたが、点が伸びない。`top` で DB のプロセスが CPU を使い切っている。
- **やり方**: 先に DB の改善（インデックス、N+1、クエリの往復をまとめる、キャッシュ）をする。DB 自体を速くしないまま、アプリを増やしても、DB の接続数と負荷が増えるだけになる。
- **確かめ方**: アプリの台の増減の前後で、DB の CPU と 1 秒あたりのクエリ数を比べる。
- **危険**: アプリを増やすと、DB への総接続数が増える（上の項）。
- **出典**: 実例: kirikiriyamama（ISUCON10 予選。アプリを 3 台に増やしたが大きく効かず、DB がボトルネックだった）。

## 読み取りのレプリカ

### 読み取りを別の台の DB に逃がす（レプリカ）

- **効く条件**: 読み取りが大半で、DB の CPU が読み取りで飽和している。または台の間の遅延が大きく、各台の近くで読みを済ませたい。
- **やり方**:
  - MySQL: レプリケーションは既定で**非同期**。書き込みは source だけ、読み取りは 1 台以上のレプリカへ。
  - PostgreSQL: ストリーミングレプリケーションも既定で非同期。`hot_standby = on` のスタンバイは**読み取り専用**で、`SELECT` は動くが、DML・DDL・`SELECT ... FOR UPDATE`・`nextval`・一時テーブルの書き込みは拒否される。
  - アプリの読み取りと書き込みの接続先を分ける。トランザクション内の読みは primary に寄せる。
  - スタンバイでは、WAL の適用と読み取りが衝突すると、適用を遅らせるか、読み取りを打ち切る（`max_standby_streaming_delay`。`hot_standby_feedback` で、primary の VACUUM による打ち切りを避けられるが、primary が膨らむ）。
- **確かめ方**: レプリケーションの遅れ（PostgreSQL は `pg_stat_replication`）。書いた直後の読みが古くならないか（下の危険）。
- **危険**: **非同期のレプリカは、書いた直後の読みが古い。** 「書き込みが成功した後の読みには、その結果を反映する」という仕様（read-after-write、権限・公開範囲の変更の即時反映）に違反して、critical になりうる。レプリカへ逃がしてよいのは、仕様が鮮度を許す読みだけ。同期にするなら、commit が待つ（下の項）。レプリカにも初期化の結果を伝える（初期化の `TRUNCATE` と読み取りが衝突する）。台が止まると、同期なら全書き込みが止まる。
- **出典**: [PostgreSQL: hot standby](https://www.postgresql.org/docs/16/hot-standby.html)、[PostgreSQL: warm standby（同期レプリケーション）](https://www.postgresql.org/docs/16/warm-standby.html)、[MySQL: replication](https://dev.mysql.com/doc/refman/8.0/en/replication.html)。手元の実例・設計: （案 (b')「非同期のスタンバイ」は削除・ブロック・友達の解除が遅れて見え、critical になりうるので不可）。

### 同期レプリケーションの待ち方（synchronous_commit）と、永続化を弱めない

- **効く条件**: レプリカを同期にして読みの整合を保つが、書き込みが遅い（commit が遠い台の応答を待つ）。
- **やり方**: PostgreSQL の `synchronous_commit` の値で、commit が待つ範囲が決まる。
  | 値 | commit が待つもの |
  | --- | --- |
  | `off` | 何も待たない（WAL のフラッシュ前に成功を返す） |
  | `local` | ローカルの WAL のフラッシュだけ |
  | `on`（既定） | 同期スタンバイが受信し、フラッシュするまで |
  | `remote_write` | スタンバイが受信し、書き込むまで（ディスクへのフラッシュは保証しない） |
  | `remote_apply` | スタンバイが適用し、読み取りで見えるまで |
  - `synchronous_standby_names` は `ANY n (a, b, c)`（クォーラム）か `FIRST n (...)`（優先度）。空なら、`remote_*` も `on` と同じく、ローカルのフラッシュだけを待つ。
  - 書き込みごとに設定を変えられる（`SET LOCAL synchronous_commit TO off;` をトランザクション内で）。**どの書き込みが別の台から読まれるか**を表にして、待ちが要るものだけ待つ。
  - レプリケーションスロットは、スタンバイが止まっても primary が WAL を捨てないようにする。`max_slot_wal_keep_size` で、WAL がディスクを埋めるのを防ぐ。
- **確かめ方**: commit の所要（トレース）、`pg_stat_replication` の遅れ、アプリの書き込みの p50・p90。
- **危険**: **`fsync = off` は、クラッシュ・停電の後に回復できないデータ破壊を起こしうる**（公式の注意）。`full_page_writes = off` も同様の危険（破損するページを検出できなくなる）。`synchronous_commit = off` は、直近の commit を失いうる（最大で `wal_writer_delay` の 3 倍、既定で約 600ms）が、データの不整合は起こさない。**ベンチ中に書いたデータが再起動後に残ること（永続化）が失格の条件**なので、`fsync` を切る・`synchronous_commit` を緩めるのは、追試・再起動試験に通るか確かめてから。スタンバイが 1 台でも止まると、同期の書き込みは全部止まる（`ANY n` の n を減らして reload で戻す）。
- **出典**: [PostgreSQL: WAL の設定（synchronous_commit、fsync、full_page_writes）](https://www.postgresql.org/docs/16/runtime-config-wal.html)、[PostgreSQL: 同期レプリケーション、レプリケーションスロット](https://www.postgresql.org/docs/16/warm-standby.html)。

## 振り分け

### パス・メソッド・機能で振り分ける

- **効く条件**: 重い処理（bcrypt のログイン、画像の検査、検索）が 1 台の CPU を食う。台ごとの CPU・得点への寄与が違う。
- **やり方**: nginx の `location` と `map` で、処理先の upstream を分ける（03 章）。
  ```nginx
  map $request_method $upstream_for_method {
    GET     app_read;
    HEAD    app_read;
    default app_write;
  }
  ```
  実例: bcrypt を使う `/login` だけを 2・3 台目のアプリへ振る（matsuu、ISUCON9 予選）。画像更新の API を別の台で受け、実ファイルは内部の通信で 1 台に書く。DNS（PowerDNS とその DB）を空いた台へ移す。計算量の大きいマッチングだけを別サーバーへ RPC する（感想戦）。
- **確かめ方**: アクセスログの `$upstream_addr`、台ごとの CPU と応答時間。
- **危険**: ログイン後のセッションを別の台で読めること（セッションの共有。下の項）。**書き込みと読みで台が分かれると、書いた直後の読みが反映されないことがある。** 重い処理を別の台へ逃がしても、保存先への書き込み応答の直後に読めること、転送失敗の扱い、保存先の認証と権限を保つ。パスで振り分けるときは、`location` の一致の範囲の誤りに気をつける。ロックが必要な URI だけを 1 台に寄せる分散は通らなかった実例がある。
- **出典**: 実例: matsuu、bcrypt のログインだけ別の台、acidlemon（ISUCON12 予選の作問者の解答。テナント名の長さで台を分けた）。

### 利用者・キーで固定する（sticky）

- **効く条件**: 状態（メモリのキャッシュ、ルームの状態、WebSocket の接続）をアプリのプロセスが持つ。複数台に振ると、状態が台ごとに分かれて壊れる。
- **やり方**: 同じ利用者・同じルームを同じ台に固定する。
  ```nginx
  upstream app {
    hash $cookie_session consistent;    # キーで固定。台が増減しても再配置が少ない
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
  }
  ```
  `ip_hash` は IPv4 の先頭 3 オクテットで固定する（ベンチが少数の IP から送ると偏る）。ルームのように数が少ないものは、ハッシュだと偏るので、中央で割り当てを持つ（ISUCON7 本選の実例: 4〜6 部屋しかないと 1 台に集中しうる）。割り当ては、部屋数だけでなく CPU の負荷でも選べる。
- **確かめ方**: 台ごとの接続数と CPU。偏り。
- **危険**: 割り当てを管理する場所（Redis など）が新しいボトルネック・単一障害点にならないようにする。同時の割り当てと、切断時の減算。台が落ちたときの再割り当て。
- **出典**: [nginx upstream（hash、ip_hash）](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)。実例: cnosuke（ISUCON7 本選）。

### 振り分けだけでは速くならない

- **効く条件**: 負荷を均等にすれば速くなる、と期待しているとき。
- **やり方**: 台ごとのアプリの能力（CPU）がボトルネックのときだけ効く。DB・帯域・共通のロック・共有のキャッシュがボトルネックなら、振り分けの前に、そちらを直す。
- **確かめ方**: 片方の台だけで測った性能、振り分けた後の合計の性能。
- **危険**: `least_conn` でアプリを 2 台に振ってスコアが下がり、約 30 分かけて戻した実例がある（ISUCON13）。KeepAlive を有効にした複数台で、点が約 67,000 から 30,000 に落ちて戻した実例もある。

## 台をまたぐ共有（セッション・キャッシュ・画像）

### セッションの共有（Redis・memcached・Cookie・DB）

- **効く条件**: アプリが複数台・複数プロセスになる。メモリに持っていたセッションが、別の台で見えない。ログイン直後の要求が別の台に行って 401 になる。
- **やり方**: 次のどれかを選ぶ。
  | 方式 | 向く場面 | 注意 |
  | --- | --- | --- |
  | Redis・memcached に置く | 台が複数。読み書きが多い | 往復が増える。期限・ログアウト・永続化と認可を全プロセスで揃える |
  | Cookie に載せる（署名つき） | DB・キャッシュの参照を無くしたい | 改ざん防止、属性の更新・失効、サイズ、権限（ISUCON5 本選の実例で DB を除いて改善） |
  | DB に置く | 最も単純 | DB の負荷。往復 |
  | 台に固定（sticky） | 状態を共有したくない | 台が落ちたときの扱い |
  | メモリに持つ（1 台集約） | 1 台に集約する場合 | 再起動で消える。再起動用の退避（JSON など）が要る |
- **確かめ方**: 別の台で、ログイン直後の要求が通るか。再起動後にもセッションが有効か（仕様で求められる場合）。
- **危険**: **メモリだけに置くと、再起動で消えて失格の原因になる。** 退避の方式（正常停止時だけか、異常終了でも残るか）を確かめる。初期化でセッションを破棄する。
- **出典**: 実例: agatan（ISUCON7 予選。複数台構成に向けて、オンメモリのセッションを Redis へ）、songmu（ISUCON5 本選。Cookie セッション）、感想戦。メモリ化して再起動用 JSON に退避。異常終了での復旧は未検証、全部メモリ化は永続化が無いと本番用にならない。

### メモリキャッシュと無効化（台ごとのキャッシュは分かれる）

- **効く条件**: アプリがメモリにキャッシュを持ち、複数台・複数プロセスにした。書き込みを受けた台以外が、古い値を返す。
- **やり方**:
  - 共有が不要な設計: 読み取りだけの不変データ（マスター）は、各台が初期化の時点で読み込めばよい。
  - 共有が要る: 書き込み側から無効化を全台に送る（HTTP の内部 API、Redis の Pub/Sub、DB の更新時刻・世代番号の確認）。
  - キャッシュは**DB の正から作り直せる形**にする（再起動後、キャッシュが空でも動く）。
- **確かめ方**: 台 A で書き、台 B で読み、反映されるか。再起動後に値が消えても正しく動くか。
- **危険**: 初期化の時だけキャッシュを埋める作りは、再起動後に空になって失敗する（ISUCON10 本選の失格原因と筆者が推定）。鮮度を DB に聞く作りは、読むたびに往復する。DB の外に足したキャッシュは、DB のレプリケーションの保証の外なので、無効化と初期化を自分で作る。
- **出典**: 初期化を受けた 1 台だけでなく、別のアプリにも再読込を伝える経路を作る。

### 初期化（initialize）を全台に伝える

- **効く条件**: アプリが複数台。`POST /initialize` は 1 台にしか来ない。メモリのキャッシュ・ファイルに書いた画像・別の台の DB が古いまま。
- **やり方**: initialize を受けた台が、ほかの台の初期化（キャッシュの破棄・ファイルの削除・再読込）を内部の API で呼ぶ。全台が完了してから応答を返す。60 秒（など、マニュアルの制限）に収める。
- **確かめ方**: initialize の後、全台のキャッシュ・ファイルが初期状態か。初期化の所要の秒数。
- **危険**: **全台・全キャッシュ・複製先の初期化の取りこぼしは、整合性チェックの失敗になる。** 内部 API は外から叩けないようにする（認証）。失敗時の復旧。全台の完了前に要求を受けない。
- **出典**: 実例: tohutohu（ISUCON9 予選）、（全リージョンで整合した初期状態、独自のキャッシュ・複製先も初期化）。

### 画像・ファイルの共有（複製・集約・共有しない）

- **効く条件**: 画像をファイルに出して nginx から返す（12 章）構成で、アプリが複数台になる。アップロードを受けた台のファイルを、別の台の nginx も返せる必要がある。
- **やり方**: 次の型から選ぶ。
  | 型 | 内容 | 注意 |
  | --- | --- | --- |
  | 画像は DB に残す（共有しない） | 全台が DB から読む | DB の I/O・帯域。台の間の往復 |
  | 1 台に集約 | 画像を 1 台に置き、他の台は内部の通信でその台から取る / その台へ書く（画像の更新 API は別の台で受け、実ファイルは内部リクエストで保存先の台に書く） | その台がボトルネック・単一障害点 |
  | 全台に複製 | 書き込みを受けた台が、全台に配る（WebDAV の PUT、rsync など。全台に複製して配信可能な台を増やす） | 複製完了前の読み取り。更新・削除の整合。**台ごとの更新時刻・ETag の差で 304 が効かなくなる** |
  | 読み手が必要なときに取りに行く（miss で取得） | 書いた台が持ち主。他の台は miss のときだけ取る | 台が落ちるとその台の画像は取れない。初回の取得が遅い |
  - nginx で WebDAV を受けるなら `ngx_http_dav_module`（既定では入らない。`PUT` の `Date` ヘッダで更新時刻を指定できる）。複製した画像の更新時刻を元に揃えると、条件付き GET が台をまたいで効きやすくなる可能性がある（は事後の推定で、確定した原因ではない）。
  - **ルーターの IP を宛先にして別の台へ届かせる接続は禁止された**。相手の台のプライベート IP へ直接つなぐ。
- **確かめ方**: 台 A でアップロードした画像を、台 B の nginx から取得できる（`curl` で、アップロード直後に）。更新・削除の後の挙動。複製の遅れ。
- **危険**: 書き込み直後の読み取り（アップロード応答の直後に GET が来る）で、複製が間に合わないと 404 になる。削除・無効化した画像を別の台が返し続けない（仕様の猶予内か）。保存先の認証と権限。画像の更新が全台に反映される前に、古い画像を返さない。

### 台の入口を増やす（ベンチが複数の台を叩く場合）

- **効く条件**: 公開側の帯域・nginx の CPU が 1 台の入口に集まって飽和している。ベンチが複数の台を対象にできる（問題による）。
- **やり方**: 複数の台をベンチの対象にして、公開側の帯域を分散する。DB 用の台でも nginx を入口にした実例がある（ISUCON7 予選）。全入口で同じデータと認証を扱えること。
- **確かめ方**: 台ごとの外向きの帯域と応答時間。
- **危険**: 複数のターゲットを指定してよいか、マニュアルで確かめる（失格に直結しうる）。全入口で同じ状態を見せる必要がある。
- **出典**: 実例: eagletmt（ISUCON7 予選）。

## 台の間の通信

### プライベート IP で接続する（ルーター・遅延・帯域の制限）

- **効く条件**: 台の間の通信（nginx → アプリ、アプリ → DB、台 → 台の画像取得）を設計するとき。
- **やり方**: 相手の台の**プライベート IP** へ接続する。台の間の IP、ポートを `servers/<台>/` の設定で台ごとに持つ。セキュリティグループで、台の間のポートを開ける（新しいポートの開放が許されることが多い。マニュアルで確かめる）。
- **確かめ方**: `nc -vz <相手のプライベート IP> <ポート>`。ベンチ後の台の間のトラフィック。

### 台をまたぐ keepalive とタイムアウト

- **効く条件**: nginx から別の台のアプリへ、アプリから別の台の DB・内部 API へ、毎回接続を作っている。往復遅延が大きく、接続の確立が 2 往復かかる（TCP の握手と、最初の要求）。
- **やり方**: nginx の upstream に `keepalive`（03 章）。アプリの HTTP クライアントは接続を使い回す（13 章）。往復遅延が大きい経路では `tcp_slow_start_after_idle = 0`（02 章）。
- **確かめ方**: 新しい接続の数、`$upstream_connect_time`。
- **危険**: アイドル接続のタイムアウトを、相手より短くそろえる（切れる瞬間の要求が失敗する。03 章）。
- **出典**: 実例: tkuchiki（ISUCON9 本選。複数台構成への変更時に upstream を keepalive に）。往復遅延と keepalive の効果は 2.1。

### 台の間の往復遅延を見積もる（往復の回数 × 遅延）

- **効く条件**: 台の間の遅延が数 ms 以上。台をまたいで DB・API を呼ぶ構成。
- **やり方**: 1 リクエストが台をまたぐ往復の回数を数え、「往復の回数 × 往復遅延」を応答時間の下限として見積もる。往復の回数を減らす手（クエリをまとめる、書き込みを DB の近くで 1 往復にする、読みを手元のレプリカで済ませる）を先に考える。
- **確かめ方**: アクセスログの最小の応答時間が、遅延の倍数に並ぶ。
- **危険**: 計算せずに台を増やすと、往復が増えるだけになる。

## 運用（設定のズレ・再起動・障害）

### 台ごとの設定をリポジトリで管理し、1 台ずつ・全台同時に再起動して確かめる

- **効く条件**: 台が複数。設定が台ごとに違う。元の台にだけ起動設定がある。
- **やり方**: 台ごとの設定（systemd の unit、nginx、sysctl、env）を `servers/<台>/` に置き、デプロイで配る。構成を変えたら、設定（接続先・台のリスト）と構成の記録を同時に直す。**1 台ずつ再起動して、その台の自動起動を確かめる。最後に全台を同時に再起動する。**
- **確かめ方**: 再起動の後、手作業なしでアプリが動き、ベンチ中に書いたデータが残っていること。
- **危険**: **再起動の後に `systemctl start` などの手作業が要るなら失格。** 実例: 元の台にだけ Compose の起動設定があり、移設先の台では unit が無かった（1 台ずつ再起動して発見）。全台が起動しきる前に来た要求で DB の接続エラーが出て、修正せず終わった使わなくなったサービスが再起動で復活する。
- **出典**: 実例: fujiwara（ISUCON6 本選）、songmu（ISUCON5 本選）、（再起動試験）。

### 同期レプリカが止まったときの戻し方

- **効く条件**: 同期レプリケーション（上の項）を使っている。スタンバイの台が止まった・つながらなくなった。
- **やり方**: すぐに `synchronous_standby_names` からその台を外す（reload だけで効く）。その台の nginx を「全部 primary へ」に戻す。再起動試験で、primary が先に上がっても、スタンバイがつながるまで書き込みが待つだけで、データが失われないことを確かめる。
- **確かめ方**: `pg_stat_replication`、書き込みが通ること。
- **危険**: スタンバイが 1 台でも止まると、同期の書き込みは全部止まる。
- **出典**: [PostgreSQL warm standby](https://www.postgresql.org/docs/16/warm-standby.html)（同期スタンバイが失われたときの対処）。

## よくある失敗

1. **台を増やす前に、ボトルネックを確かめない。** DB がボトルネックならアプリを増やしても効かない。
2. **振り分けて、点が下がる。** `least_conn`・パスでの振り分けは、DB・帯域・ロックがボトルネックだと効かない。
3. **役割を変えた台の旧サービスが動き続ける。** 二重実行・再起動での復活。
4. **台の間の通信が切れる。** tcpwrapper・ファイアウォール・MTU。
5. **再起動で、起動設定が無い台がある。** 1 台ずつ、全台同時に再起動する。
6. **メモリの状態が台ごとに分かれる。** セッション・キャッシュ・ルームの状態。共有するか、固定するか、DB の正から作り直せる形にする。
7. **非同期のレプリカに、書いた直後の読みを逃がす。** read-after-write を壊して critical に。
8. **初期化を全台・全キャッシュに伝えない。** 整合性チェックの失敗。
9. **永続化を弱める。** `fsync` を切る、メモリだけに置く、tmpfs に置く。再起動試験で失格。
10. **台の間の通信の宛先を点検しない。** ルーターの IP を宛先にする接続は禁止された。
11. **平均の負荷で構成を決める。** 山の数秒で決める（capacity-plan）。
12. **画像を複数台に複製して、更新時刻・ETag が揃わず 304 が効かない。** 同じ URI を各台から取得して、ヘッダを比べる。
