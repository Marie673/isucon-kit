# スコアのモデル

当日の最初の 90 分でやる。実装の改善より先。雛形は `docs/design.md` の C。

## 手順

### 1. マニュアルから式を書く（30 分）
1. 配点の表・倍率・減点・失格の条件を全部拾い、`docs/design.md` の C1 に式で書く。
2. 「件数」が何で決まるかを書く。たいていは「ベンチが送る利用者・リクエストの数 × 1 人あたりの操作」で、前者はアプリの速さで増減する。
3. **項ごとの上限**を書く。実際のベンチが項の上限を超えたら、モデルが間違っている。どの前提が違うかを、ボトルネック表の最上位の問いにする。
4. 一番大きい項を決める。以後の判断はこの項から。
5. **スコアがどう増えるかを説明できるようにする。** スコアの式の項ごとに（例: 利用者がどう増えるか、1 人あたりのスコアをどう増やすか）、何で決まり、今どれだけ取れているかを書く。分からなければ【推】で置き、ベンチのたびに直す。**合計のスコアの目標は書かない。** 項の上限は、どの項に伸びしろがあるかを見るために使う。

### 2. 負荷が増える条件と、利用者の行動（30 分）

skill `app-profile` と並べてやる。動線・増える条件の詳細は `docs/design.md` の B に書き、ここにはスコアに関わる結論だけを写す。

1. マニュアルの「負荷ベンチ」「シナリオ」の節から、ベンチが負荷を増やす条件・やめる条件を書く。
2. **利用者が何を見て次の行動を決めるか**を表にする。スコアの構造はここに隠れる。
   - 例: 利用者が直前の応答の中身を見て次の操作を決めるとき、その時点で中身が空だと、後のスコアが取れない。
3. 一斉に同じことをする瞬間（ピーク）と、その大きさを書く。design.md の D の入力になる。

### 3. ベースラインの記録で確かめる（30 分、ベンチ 1 本目の後）
1. ベンチの出力・アクセスログ・（あれば）リクエストの記録から、モデルの各項の実際の値を出す。
2. **スコアの帳簿のスクリプト**を作る。ベンチごとに「区分 × 段階で、どの理由でスコアを落としたか」を表で出すもの。出力は `docs/design.md` の C5 の形。メインエージェントが `isu-bench` の後に毎回流す。
   - **取りこぼしをスコアに直す**: 失敗・断った件数 × 成功していたら取れたスコア。減点とは別の列にする。
   - **ボーナスと減点を分けて数える**（差し引きの 1 つの数にしない）。ボーナスの条件（`docs/design.md` の A1）ごとに、取れた件数と取れなかった件数を出す。
   - 最後に「今のスコア・取りこぼしの合計・項ごとの値と上限」を出す。
3. モデルとずれた所を「6. ここから出る問い」に書く。ボトルネック表の候補になる。

## 書き方

- 数字には出典（マニュアルの節・job 番号）と印（【M】マニュアルだけで分かる、【B】ベンチの記録が要る、【推】推測）を付ける。
- 推測で埋めた項は、測る手段を一緒に書く。
- 書き終えたら、作戦ボードに出典と要点を書く。

## よくある見落とし

- スコアの大半が「速さ」ではなく「利用者の行動の連鎖」で決まっている。
- 区分・段階で倍率や負荷の大きさが違い、一番大きい区分がボトルネックになる。
- 最後の段階だけ条件が変わる。
- タイムアウトやエラーが「スコアを引く」だけでなく「負荷を増やさない」条件になっている。
- 負荷（人数）に上限があり、届いた後の伸びしろは 1 人あたりの操作だけになる。区分・段階ごとの人数をベンチごとに並べ、規模が違っても同じ所で止まるなら、上限を疑う。
- ボトルネックが残っているのに、守りに入る。効く項を止めているものを、凍結まで取り続ける。
- ボーナスと減点を差し引きの 1 つの数にまとめ、ボーナスを取りこぼしているのが見えない。
- ベンチが「got=400, want=200」のように仕様の値で失敗を言うのを、取り合い・ベンチのせいにする。まず、こちらの判定が仕様（`docs/design.md` の A）とずれている前提で突き合わせる。
